# Windows UI parity contract

This contract fixes the Windows shell entry points against the macOS reference so the port can add functionality without drifting from the existing product shape.

## Reference evidence
- macOS navigation order comes from the current TDSC mac branch `origin/tdsc-2026-01-0318-ios-sim-fix:Sources/SkyBridgeCompassApp/Dashboard/Navigation/NavigationItem.swift`: Dashboard, Device Discovery, USB Management, File Transfer, Remote Desktop, Quantum, System Monitor, Settings.
- macOS dashboard routing is implemented in `origin/tdsc-2026-01-0318-ios-sim-fix:Sources/SkyBridgeCompassApp/Dashboard/DashboardView.swift`.
- macOS top bar visible order includes connection state, FPS/diagnostics, notifications, and theme in `origin/tdsc-2026-01-0318-ios-sim-fix:Sources/SkyBridgeCompassApp/Dashboard/TopBar/TopNavigationBarView.swift`; that view also owns the manual connection sheet bindings (`showManualConnectSheet`, IP, port, pairing code), while the visible manual-connect opener may live in the dashboard/device-discovery content surface.
- macOS current-path modularization evidence comes from `origin/tdsc-2026-01-0318-ios-sim-fix:Docs/CoreLayering.md` and handshake reality comes from `origin/tdsc-2026-01-0318-ios-sim-fix:Docs/ProtocolAlignmentPlan.md`; the transport-matrix ADR remains on `origin/tdsc-2026-01-0318-ios-sim-fix-20260211-adr:Docs/ADR-0001-SkyBridge-Core-Transport-Matrix.md`.
- macOS manual connection uses IP Address blank by default, Port `11550`, Pairing Code blank by default, a `Manual Connect` entry point, and a final `Connect` action. The Windows read-only boundary mirrors those fields first, while live connection remains pending behind pairing, trust, Core preflight, and native adapter work.
- macOS cross-network discovery uses `Dynamic Encrypted QR Code` with `Generate QR Code`, `Scan QR Code`, `Waiting for connection...`, `Regenerate`, accepted URI formats `skybridge://connect/<base64url-json>` and `skybridge://connect?data=<base64url-json>`, plus `Smart Connection Code` with `Generate Code`, `Copy`, `Regenerate`, and `Connect`. QR evidence includes `SignedQRPayload`, `DynamicQRCodeData`, `QRCodeSignatureEnvelope`, `QRCodeSignatureQuery`, `sessionID`, `deviceFingerprint`, `publicKey`, `signingPublicKey`, `signature`, `signatureTimestamp`, `expiresAt`, `sig`, `pk`, `ts`, `fp`, `signatureBase64`, `publicKeyBase64`, `timestamp`, and `publicKeyFingerprint`. The short-code input is exactly 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`.
- macOS feature surfaces also include device discovery modes, file transfer actions/history, remote desktop session controls, system monitoring, settings tabs, security/trust/approval, and menu bar quick actions.

## Windows shell contract
- The Windows side navigation must keep the same feature order as the macOS `NavigationItem` list, and its glyph/title/status row must render through `NavigationItemTemplate` so the primary product entry points stay testable outside inline ListView markup.
- The first visible viewport must be the product workspace, not a landing page. The shell is left navigation, top status/action bar, and main workspace.
- The top bar must surface the selected feature, Core status, connection status, FPS/diagnostics, notifications, theme, and Windows connection controls from the shared session view model. `TopBarStatusClient` is the replaceable read-only boundary for connection/FPS/notification/theme status values, resolved status snapshots, action-detail snapshots, slot lookup, and notification/theme defaults, `TopBarStatusSlot` is the stable scalar mapping key, and `WorkspaceActionCatalogClient` owns the ordered global session/top-bar action catalogs (`SidebarSessionActions`, `TopBarActions`, `SessionControlActions`), initial surface load order, dynamic surface refresh order, plus stable `WorkspaceActionCommandId`, `WorkspaceActionGateId`, and `WorkspaceActionDetailSlot` roles so the XAML keeps mac-parity positions while providers remain modular. All catalog-backed buttons must render through shared XAML resources (`WorkspaceActionButtonTemplate`, `WorkspaceActionButtonWithDetailTemplate`, `SidebarWorkspaceActionButtonTemplate`, and the shared action `ItemsPanelTemplate` resources) so title-bar, toolbar, quick-action, and session-control positions share one style and one `IsEnabled` binding path. Repeated `Title` / `Value` / `Detail` metric cards must render through `WorkspaceMetricCardTemplate` and `WorkspaceMetricCardItemsPanel`, starting with Dashboard metrics and USB Management stats; Dashboard metric values must come from `DashboardMetricsClient.Metrics`, while the scalar status properties remain available for status/top-bar logic. Repeated read-only `Label` / `Value` / `Detail` fact rows must render through `WorkspaceFactRowTemplate` when they share the same column contract, including Device Discovery browser/manual/cross-network/pairing/preflight facts plus File Transfer security, Remote Desktop control, Quantum/Core diagnostic, and System Monitor overview/detail facts. Repeated `Label` / `State` / `Detail` indicator rows must render through `WorkspaceStateRowTemplate`, starting with System Monitor health/thermal/load indicators. Settings tab `Title` / `Detail` rows must render through `SettingsTabItemTemplate`; Settings four-column `Section` / `Label` / `Value` / `Detail` rows must render through `SettingsDetailRowTemplate`, and four-column `Key` / `Title` / `State` / `Detail` rows must render through `SettingsActionRowTemplate`. Manual connection remains a Device Discovery entry point until the mac opener location is fully readable from the TDSC partial clone; Windows must still keep the IP, port, pairing-code, `Manual Connect`, and final `Connect` fields visible in their verified Device Discovery order. Network/IP/speed/latency indicators are optional on macOS settings and may remain provider-pending on Windows, but connection/FPS/notification/theme positions must stay visible and ordered.
- Device Discovery discovered-peer rows must render through `DiscoveredPeerItemTemplate` so mac/iOS candidates keep one testable `DisplayName` / `DeviceId` / `Platform` / `ServiceKind` / `CapabilitiesSummary` / `PublicKeyFingerprint` / `TrustSummary` layout outside inline `ListView.ItemTemplate` markup.
- USB device rows, File Transfer queue/history rows, and Remote Desktop session rows must render through `UsbDeviceItemTemplate`, `FileTransferQueueItemTemplate`, `FileTransferHistoryItemTemplate`, and `RemoteDesktopSessionItemTemplate`; `MainWindow.xaml` must not define inline `ListView.ItemTemplate` blocks for these mac-parity workspaces.
- Unimplemented feature pages may show a disabled or placeholder workspace, but their navigation entry must remain present so parity gaps are visible and testable. Device Discovery is no longer a pure placeholder: it has mac-parity scan controls, a read-only Windows DNS-SD browser boundary, default editable input values from `DeviceDiscoveryInputDefaultsClient`, a manual target row (`Manual Host / IP`, `Port`, `Code`, `Manual Connect`), cross-network QR/code controls (`Dynamic Encrypted QR Code`, `Generate QR Code`, `Scan QR Code`, `Smart Connection Code`, `Generate Code`, `Copy`, `Regenerate`, `Connect`), a manual Core-validated Bonjour service/TXT parser, a pairing-code validator, and a `Prepare Connection` preflight view while real DNS-SD browsing, trust-store persistence, signaling, and native adapter launch remain pending. `WorkspaceActionCatalogClient` owns the ordered visible Device Discovery and cross-network command groups plus their command role IDs (`Parse TXT`, `Validate Pairing`, `Prepare Connection`; `Extended Search`, `Manual Connect`, `Start Scan`, `Stop Scan`, `Refresh`; `Generate QR Code`, `Scan QR Code`; `Generate Code`, `Copy`, `Regenerate`, `Connect`) while `SessionViewModel` keeps the actual command objects and readiness gates.
- Device Discovery scan controls must stay in the same functional order as the TDSC mac local-scan surface where practical: compatibility mode, extended search, manual connect, start/stop scan, refresh, search, then manual target fields and device list/results. Windows may keep manual target/TXT/pairing/preflight controls visible while native DNS-SD and trust persistence are pending, but it must not hide or reorder the scan/search/refresh/start/stop entry points.
- USB Management must keep the macOS device-management shape visible: refresh, last scan, MFi certified count, Android device count, storage device count, total device count, empty state, device list, device ID, vendor ID, product ID, serial number, connection interface, and capabilities. `WorkspaceActionCatalogClient` owns `UsbManagementHeaderActions` (`Refresh Devices`) so the header button position remains testable outside XAML. Until Windows USB providers are wired, MFi/Android/vendor/product/serial details must be labeled pending instead of synthesized.
- File Transfer must keep the macOS quick-action shape visible: refresh plan, select files, select folder, QR sharing, transfer queue, transfer history, HMAC, and signature status. `WorkspaceActionCatalogClient` owns `FileTransferHeaderActions` (`Refresh Plan`) and the ordered quick-action catalog (`Select Files`, `Select Folder`, `Generate QR`) so button position remains testable outside XAML. Until the real file picker and transport are wired, those actions may remain disabled but the queue/history/security workspace must be driven by Core contracts.
- Remote Desktop must keep the macOS session shape visible: refresh sessions, recommended connect, advanced connect, connection mode, active/recent sessions, performance overlay, quality controls, settings, fullscreen, and disconnect. `RemoteDesktopProfileCatalogClient` owns the shared bitrate/framerate profile options, defaults, and selection-status text used by both the Remote Desktop workspace and Session Controls, while `WorkspaceActionCatalogClient` owns `RemoteDesktopHeaderActions` (`Refresh Sessions`) and the ordered Remote Desktop quick-action catalog (`Recommended Connect`, `Advanced Connect`, `Performance Overlay`, `Quality`, `Settings`, `Full Screen`, `Disconnect Session`) so button position remains testable outside XAML. Until live capture/input/video transport are wired, those actions may remain disabled but the session/control workspace must be driven by Core contracts.
- Quantum/Core Diagnostics must keep the Core-owned protocol facts visible behind an explicit header action. `WorkspaceActionCatalogClient` owns `QuantumDiagnosticsHeaderActions` (`Run Diagnostics`) while `CoreDiagnosticsClient` owns transport binding digest, suite, SBP2, channel, and frame facts; running diagnostics must not initiate a session.
- System Monitor must keep the macOS monitoring shape visible: refresh metrics, monitoring status, stop monitoring, advanced/helper monitoring, overview metrics, detailed monitoring cards, health, thermal, and load indicators. `WorkspaceActionCatalogClient` owns the ordered System Monitor header/control catalogs (`Refresh Metrics`; `Monitoring`, `Stop Monitoring`, `Enable Advanced Monitoring`) so button positions remain testable outside XAML. Until ETW/GPU/thermal providers are wired, unsupported metrics must be labeled pending instead of synthesized.
- Settings must keep the macOS preference-workspace shape visible: General, Network, Devices, File Transfer, Remote Desktop, System Monitor, Permissions, and Advanced tabs; refresh status, export/import/reset actions; permission/system-settings actions; apply/default/reset-monitor actions; File Transfer, Video Transfer, Remote Desktop, System Monitor, and PQC/Core policy fields. `WorkspaceActionCatalogClient` owns `SettingsHeaderActions` (`Refresh Status`), the ordered visible Settings toolbar catalog (`Export`, `Import`, `Reset`, `Request Permission`, `Open System Preferences`), and maintenance catalog (`Apply Settings`, `Restore Defaults`, `Reset Monitor Data`) so button positions remain testable outside XAML. Until persistence and providers are wired, high-risk writes must stay disabled and separated from read-only refresh.
- Connection, heartbeat, and disconnect commands must stay bound to `SessionViewModel` through `WorkspaceActionCommandId` roles and must not invent per-page state. Their enabled state and session gate snapshot must come from `SessionCommandStateClient`, workspace feature command gates and Device Discovery/Cross-network action-readiness composition must come from `WorkspaceCommandStateClient`, and their initial, pending, completed, and engine-state status text must come from `SessionStatusClient`, not ViewModel string literals, inline `EngineConnectionState` command gates, scattered session command booleans in `WorkspaceCommandGateRequest`, inline `!IsBusy && Is...Selected` workspace gates, inline `CanUse...() && readiness` composition, or a local engine-state message switch.
- Workspace action enabled/detail role resolution and surface plans must come from `WorkspaceActionCatalogClient` through `WorkspaceActionGateSnapshot`, `WorkspaceActionDetailSnapshot`, `BuildResolvedSnapshot`, `BuildInitialSurfaces`, and `BuildDynamicRefreshSurfaces`; top-bar detail snapshots must come from `TopBarStatusClient.BuildWorkspaceActionDetailSnapshot`; workspace gate snapshots and selected-feature/busy command gates must come from `WorkspaceCommandStateClient`. `WorkspaceActionRenderContextBuilder` assembles the current gate/detail context, and `WorkspaceActionSurfaceLoader` maps catalog actions to XAML-bound surfaces and commands, while `SessionViewModel` may provide current scalar state; it must not own enabled/detail switch logic, per-action resolved enabled/detail calls, action gate request construction, or hardcoded load/refresh surface lists.
- Reusable dashboard/action/fact/list item record adapters must live in `WorkspaceItemViews.cs`, bindable command creation and `WorkspaceActionCommandId` role registration must live in `WorkspaceCommandBindings.cs`, dashboard metric projection must live in `DashboardMetricsUpdater.cs`, top-bar status/action projection must live in `TopBarStatusUpdater.cs`, generic collection replacement must live in `WorkspaceCollectionProjector.cs`, read-only workspace snapshot projection must live in `WorkspaceSnapshotApplier.cs`, connection input reset/cleanup state must live in `ConnectionWorkspaceInputCoordinator.cs`, and the reusable async command adapter must live in `AsyncRelayCommand.cs`; `SessionViewModel` may coordinate observable collections and consume generated commands, but it must not own repeated `...View` record definitions, command-role registration, dashboard snapshot projection, top-bar update projection, collection copy loops, snapshot collection maps, reset reasons, direct pairing/preflight clears, or the `AsyncRelayCommand` implementation.
- Selected-feature predicates must come from `FeatureCatalogClient.IsSelected`; `SessionViewModel` may expose binding booleans, but it must not own direct `SelectedFeature.Id == FeatureEntryId.*` comparisons.
- Busy-state errors must be routed by explicit `WorkspaceErrorScope` values through `WorkspaceErrorStatusClient`; `SessionViewModel` must not inspect `SelectedFeature` or `Is...Selected` inside the catch path to decide which workspace status receives an error.
- Optional service fallback clients must live in `Services/UnavailableClientStubs.cs`; `SessionViewModel` may instantiate them as constructor defaults, but must not define unavailable service classes inline.
- Runtime protocol facts must come from Rust Core contracts: transport selection, transport binding digest, channel mapping, connection planning, suite selection, frame metadata, and engine diagnostics. Pairing public keys and pairing/trust facts must come from validated `PairingMaterialSnapshot` output, not discovery `pubKeyFP` or ViewModel string assembly. Device Discovery default service/manual-port/TXT/pairing-code inputs must come from `DeviceDiscoveryInputDefaultsClient`; the view model must not own sample peer-key material. Device Discovery browser facts must come from `WindowsDiscoveryBrowserClient`, which is the replaceable Win32 `DnsServiceBrowse` boundary and feeds candidates through `CoreDiscoveryClient`; it must not synthesize trusted peers. Manual target facts must come from `ManualConnectionClient`; host/port/code input may create only a read-only `_skybridge._tcp` target snapshot, and the code must never be treated as a peer public key. Cross-network QR/code facts and Smart Connection Code input filtering/normalization must come from `CrossNetworkConnectionClient`; QR/code input may create only a read-only schema/signature/expiry snapshot for `SignedQRPayload`, `DynamicQRCodeData`, `QRCodeSignatureEnvelope`, or `QRCodeSignatureQuery`, and Windows must report `CrossNetworkReadiness` as `idle` until the dynamic QR canonical verifier, trust approval, signaling, Core planning, and transport binding are wired. Device Discovery preflight must call `ConnectionPreflightClient` over `CoreBridge.PlanConnectionAsync`, `CoreBridge.ComputeTransportBindingDigestAsync`, and channel mapping before any real adapter launch is enabled. Quantum/Core diagnostics must call `CoreDiagnosticsClient` over `CoreBridge`, including `CoreBridge.ComputeTransportBindingDigestAsync`, not re-derive protocol state in XAML or view-model code.
- The Extended Search countdown and DNS-SD query order must come from `DiscoveryBrowserInputPolicy` on `WindowsDiscoveryBrowserClient`; `SessionViewModel` may bind and pass the countdown through, but must not hardcode the 15-second discovery policy.
- Discovered-peer row summaries must come from `DiscoveryBrowserPeerCandidate`; `SessionViewModel` may expose `DiscoveredPeerView` for XAML binding, but it must not reformat `PeerCapabilities` or recreate fingerprint-only trust text.
- Device Discovery parser/manual/pairing/preflight, Discovery Browser, Cross-network, Core diagnostics, USB Management, File Transfer, Remote Desktop, System Monitor, and Settings initial and pending statuses must come from `ConnectionWorkspaceStateClient.BuildInitialStatusPatch` or `BuildInitialStatus` / `BuildPendingStatus` on their service clients; `SessionViewModel` must not own `Ready` defaults, progress literals, or switch on those action enums to produce user-visible progress text.
- Core diagnostics, USB Management, File Transfer, Remote Desktop, System Monitor, and Settings completed refresh statuses must come from `BuildCompletedStatus` and `BuildCompletedStatusMessage` on their service clients; `SessionViewModel` must not format captured timestamps or own "workspace updated" text.
- Smart Connection Code readiness must come from `ICrossNetworkConnectionClient.CanConnectWithCode`, and input filtering must come from `ICrossNetworkConnectionClient.NormalizeCodeInput`; `SessionViewModel` must not hardcode casing, alphabet filtering, or the 6-character rule.
- Device Discovery parser/manual/pairing readiness and Cross-network QR scan/copy readiness must come from their service clients, then be combined with busy/selected-feature UI state through `WorkspaceCommandStateClient`; `SessionViewModel` must not own the input-policy checks or final `CanUse...() && readiness` composition.
- Prepare Connection readiness must come from `IConnectionWorkspaceStateClient.CanPreparePreflight`, using the same discovered-peer and pairing-material requirements as the preflight error path; `SessionViewModel` must not own that private-field null gate.
