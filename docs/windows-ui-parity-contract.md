# Windows UI parity contract

This contract fixes the Windows shell entry points against the macOS reference so the port can add functionality without drifting from the existing product shape.

## Reference evidence
- macOS navigation order comes from the current TDSC mac branch `origin/tdsc-2026-01-0318-ios-sim-fix:Sources/SkyBridgeCompassApp/Dashboard/Navigation/NavigationItem.swift`: Dashboard, Device Discovery, USB Management, File Transfer, Remote Desktop, Quantum, System Monitor, Settings.
- macOS dashboard routing is implemented in `origin/tdsc-2026-01-0318-ios-sim-fix:Sources/SkyBridgeCompassApp/Dashboard/DashboardView.swift`.
- macOS top bar visible order includes connection state, FPS/diagnostics, notifications, and theme in `origin/tdsc-2026-01-0318-ios-sim-fix:Sources/SkyBridgeCompassApp/Dashboard/TopBar/TopNavigationBarView.swift`; that view also owns the manual connection sheet bindings (`showManualConnectSheet`, IP, port, pairing code), while the visible manual-connect opener may live in the dashboard/device-discovery content surface.
- macOS current-path modularization evidence comes from `origin/tdsc-2026-01-0318-ios-sim-fix:Docs/CoreLayering.md` and handshake reality comes from `origin/tdsc-2026-01-0318-ios-sim-fix:Docs/ProtocolAlignmentPlan.md`; the transport-matrix ADR remains on `origin/tdsc-2026-01-0318-ios-sim-fix-20260211-adr:Docs/ADR-0001-SkyBridge-Core-Transport-Matrix.md`.
- macOS manual connection uses IP Address blank by default, Port `11550`, Pairing Code blank by default, a `Manual Connect` entry point, and a final `Connect` action. The Windows read-only boundary mirrors those fields first, while live connection remains pending behind pairing, trust, Core preflight, and native adapter work.
- macOS cross-network discovery uses `Dynamic Encrypted QR Code` with `Generate QR Code`, `Scan QR Code`, `Waiting for connection...`, `Regenerate`, accepted URI formats `skybridge://connect/<base64url-json>` and `skybridge://connect?data=<base64url-json>`, plus `Smart Connection Code` with `Generate Code`, `Copy`, `Regenerate`, and `Connect`. QR evidence includes `SignedQRPayload`, `DynamicQRCodeData`, `QRCodeSignatureEnvelope`, `QRCodeSignatureQuery`, `sessionID`, `deviceFingerprint`, `publicKey`, `signingPublicKey`, `signature`, `signatureTimestamp`, `expiresAt`, `sig`, `pk`, `ts`, `fp`, `signatureBase64`, `publicKeyBase64`, `timestamp`, and `publicKeyFingerprint`. The short-code input is exactly 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`.
- macOS feature surfaces also include device discovery modes, file transfer actions/history, remote desktop session controls, system monitoring, settings tabs, security/trust/approval, and menu bar quick actions.

## Windows shell contract
- The Windows side navigation must keep the same feature order as the macOS `NavigationItem` list, and its glyph/title/status row must render through `NavigationItemTemplate` so the primary product entry points stay testable outside inline ListView markup.
- The first visible viewport must be the product workspace, not a landing page. The shell is left navigation, top status/action bar, and main workspace.
- The top bar must surface the selected feature, Core status, connection status, FPS/diagnostics, notifications, theme, and Windows connection controls from the shared session view model. `TopBarStatusClient` is the replaceable read-only boundary for connection/FPS/notification/theme status values, `TopBarStatusSlot` is the stable scalar mapping key, and `WorkspaceActionCatalogClient` owns the ordered global session/top-bar action catalogs (`SidebarSessionActions`, `TopBarActions`, `SessionControlActions`) plus stable `WorkspaceActionCommandId`, `WorkspaceActionGateId`, and `WorkspaceActionDetailSlot` roles so the XAML keeps mac-parity positions while providers remain modular. All catalog-backed buttons must render through shared XAML resources (`WorkspaceActionButtonTemplate`, `WorkspaceActionButtonWithDetailTemplate`, `SidebarWorkspaceActionButtonTemplate`, and the shared action `ItemsPanelTemplate` resources) so title-bar, toolbar, quick-action, and session-control positions share one style and one `IsEnabled` binding path. Repeated `Title` / `Value` / `Detail` metric cards must render through `WorkspaceMetricCardTemplate` and `WorkspaceMetricCardItemsPanel`, starting with Dashboard metrics and USB Management stats; Dashboard metric values must come from `DashboardMetricsClient.Metrics`, while the scalar status properties remain available for status/top-bar logic. Repeated read-only `Label` / `Value` / `Detail` fact rows must render through `WorkspaceFactRowTemplate` when they share the same column contract, including Device Discovery browser/manual/cross-network/pairing/preflight facts plus File Transfer security, Remote Desktop control, Quantum/Core diagnostic, and System Monitor overview/detail facts. Repeated `Label` / `State` / `Detail` indicator rows must render through `WorkspaceStateRowTemplate`, starting with System Monitor health/thermal/load indicators. Settings tab `Title` / `Detail` rows must render through `SettingsTabItemTemplate`; Settings four-column `Section` / `Label` / `Value` / `Detail` rows must render through `SettingsDetailRowTemplate`, and four-column `Key` / `Title` / `State` / `Detail` rows must render through `SettingsActionRowTemplate`. Manual connection remains a Device Discovery entry point until the mac opener location is fully readable from the TDSC partial clone; Windows must still keep the IP, port, pairing-code, `Manual Connect`, and final `Connect` fields visible in their verified Device Discovery order. Network/IP/speed/latency indicators are optional on macOS settings and may remain provider-pending on Windows, but connection/FPS/notification/theme positions must stay visible and ordered.
- Device Discovery discovered-peer rows must render through `DiscoveredPeerItemTemplate` so mac/iOS candidates keep one testable `DisplayName` / `DeviceId` / `Platform` / `ServiceKind` / `CapabilitiesSummary` / `PublicKeyFingerprint` / `TrustSummary` layout outside inline `ListView.ItemTemplate` markup.
- USB device rows, File Transfer queue/history rows, and Remote Desktop session rows must render through `UsbDeviceItemTemplate`, `FileTransferQueueItemTemplate`, `FileTransferHistoryItemTemplate`, and `RemoteDesktopSessionItemTemplate`; `MainWindow.xaml` must not define inline `ListView.ItemTemplate` blocks for these mac-parity workspaces.
- Unimplemented feature pages may show a disabled or placeholder workspace, but their navigation entry must remain present so parity gaps are visible and testable. Device Discovery is no longer a pure placeholder: it has mac-parity scan controls, a read-only Windows DNS-SD browser boundary, default editable input values from `DeviceDiscoveryInputDefaultsClient`, a manual target row (`Manual Host / IP`, `Port`, `Code`, `Manual Connect`), cross-network QR/code controls (`Dynamic Encrypted QR Code`, `Generate QR Code`, `Scan QR Code`, `Smart Connection Code`, `Generate Code`, `Copy`, `Regenerate`, `Connect`), a manual Core-validated Bonjour service/TXT parser, a pairing-code validator, and a `Prepare Connection` preflight view while real DNS-SD browsing, trust-store persistence, signaling, and native adapter launch remain pending. `WorkspaceActionCatalogClient` owns the ordered visible Device Discovery and cross-network command groups plus their command role IDs (`Parse TXT`, `Validate Pairing`, `Prepare Connection`; `Extended Search`, `Manual Connect`, `Start Scan`, `Stop Scan`, `Refresh`; `Generate QR Code`, `Scan QR Code`; `Generate Code`, `Copy`, `Regenerate`, `Connect`) while `SessionViewModel` keeps the actual command objects and readiness gates.
- Device Discovery scan controls must stay in the same functional order as the TDSC mac local-scan surface where practical: compatibility mode, extended search, manual connect, start/stop scan, refresh, search, then manual target fields and device list/results. Windows may keep manual target/TXT/pairing/preflight controls visible while native DNS-SD and trust persistence are pending, but it must not hide or reorder the scan/search/refresh/start/stop entry points.
- USB Management must keep the macOS device-management shape visible: refresh, last scan, MFi certified count, Android device count, storage device count, total device count, empty state, device list, device ID, vendor ID, product ID, serial number, connection interface, and capabilities. `WorkspaceActionCatalogClient` owns `UsbManagementHeaderActions` (`Refresh Devices`) so the header button position remains testable outside XAML. Until Windows USB providers are wired, MFi/Android/vendor/product/serial details must be labeled pending instead of synthesized.
- File Transfer must keep the macOS quick-action shape visible: refresh plan, select files, select folder, QR sharing, transfer queue, transfer history, HMAC, and signature status. `WorkspaceActionCatalogClient` owns `FileTransferHeaderActions` (`Refresh Plan`) and the ordered quick-action catalog (`Select Files`, `Select Folder`, `Generate QR`) so button position remains testable outside XAML. Until the real file picker and transport are wired, those actions may remain disabled but the queue/history/security workspace must be driven by Core contracts.
- Remote Desktop must keep the macOS session shape visible: refresh sessions, recommended connect, advanced connect, connection mode, active/recent sessions, performance overlay, quality controls, settings, fullscreen, and disconnect. `RemoteDesktopProfileCatalogClient` owns the shared bitrate/framerate profile options used by both the Remote Desktop workspace and Session Controls, while `WorkspaceActionCatalogClient` owns `RemoteDesktopHeaderActions` (`Refresh Sessions`) and the ordered Remote Desktop quick-action catalog (`Recommended Connect`, `Advanced Connect`, `Performance Overlay`, `Quality`, `Settings`, `Full Screen`, `Disconnect Session`) so button position remains testable outside XAML. Until live capture/input/video transport are wired, those actions may remain disabled but the session/control workspace must be driven by Core contracts.
- Quantum/Core Diagnostics must keep the Core-owned protocol facts visible behind an explicit header action. `WorkspaceActionCatalogClient` owns `QuantumDiagnosticsHeaderActions` (`Run Diagnostics`) while `CoreDiagnosticsClient` owns transport binding digest, suite, SBP2, channel, and frame facts; running diagnostics must not initiate a session.
- System Monitor must keep the macOS monitoring shape visible: refresh metrics, monitoring status, stop monitoring, advanced/helper monitoring, overview metrics, detailed monitoring cards, health, thermal, and load indicators. `WorkspaceActionCatalogClient` owns the ordered System Monitor header/control catalogs (`Refresh Metrics`; `Monitoring`, `Stop Monitoring`, `Enable Advanced Monitoring`) so button positions remain testable outside XAML. Until ETW/GPU/thermal providers are wired, unsupported metrics must be labeled pending instead of synthesized.
- Settings must keep the macOS preference-workspace shape visible: General, Network, Devices, File Transfer, Remote Desktop, System Monitor, Permissions, and Advanced tabs; refresh status, export/import/reset actions; permission/system-settings actions; apply/default/reset-monitor actions; File Transfer, Video Transfer, Remote Desktop, System Monitor, and PQC/Core policy fields. `WorkspaceActionCatalogClient` owns `SettingsHeaderActions` (`Refresh Status`), the ordered visible Settings toolbar catalog (`Export`, `Import`, `Reset`, `Request Permission`, `Open System Preferences`), and maintenance catalog (`Apply Settings`, `Restore Defaults`, `Reset Monitor Data`) so button positions remain testable outside XAML. Until persistence and providers are wired, high-risk writes must stay disabled and separated from read-only refresh.
- Connection, heartbeat, and disconnect commands must stay bound to `SessionViewModel` through `WorkspaceActionCommandId` roles and must not invent per-page state.
- Runtime protocol facts must come from Rust Core contracts: transport selection, transport binding digest, channel mapping, connection planning, suite selection, frame metadata, and engine diagnostics. Pairing public keys and pairing/trust facts must come from validated `PairingMaterialSnapshot` output, not discovery `pubKeyFP` or ViewModel string assembly. Device Discovery default service/manual-port/TXT/pairing-code inputs must come from `DeviceDiscoveryInputDefaultsClient`; the view model must not own sample peer-key material. Device Discovery browser facts must come from `WindowsDiscoveryBrowserClient`, which is the replaceable Win32 `DnsServiceBrowse` boundary and feeds candidates through `CoreDiscoveryClient`; it must not synthesize trusted peers. Manual target facts must come from `ManualConnectionClient`; host/port/code input may create only a read-only `_skybridge._tcp` target snapshot, and the code must never be treated as a peer public key. Cross-network QR/code facts and Smart Connection Code input filtering must come from `CrossNetworkConnectionClient`; QR/code input may create only a read-only schema/signature/expiry snapshot for `SignedQRPayload`, `DynamicQRCodeData`, `QRCodeSignatureEnvelope`, or `QRCodeSignatureQuery`, and Windows must report `CrossNetworkReadiness` as `idle` until the dynamic QR canonical verifier, trust approval, signaling, Core planning, and transport binding are wired. Device Discovery preflight must call `ConnectionPreflightClient` over `CoreBridge.PlanConnectionAsync`, `CoreBridge.ComputeTransportBindingDigestAsync`, and channel mapping before any real adapter launch is enabled. Quantum/Core diagnostics must call `CoreDiagnosticsClient` over `CoreBridge`, including `CoreBridge.ComputeTransportBindingDigestAsync`, not re-derive protocol state in XAML or view-model code.
- The Extended Search countdown and DNS-SD query order must come from `DiscoveryBrowserInputPolicy` on `WindowsDiscoveryBrowserClient`; `SessionViewModel` may bind and pass the countdown through, but must not hardcode the 15-second discovery policy.
- Discovered-peer row summaries must come from `DiscoveryBrowserPeerCandidate`; `SessionViewModel` may expose `DiscoveredPeerView` for XAML binding, but it must not reformat `PeerCapabilities` or recreate fingerprint-only trust text.
- Discovery Browser and Cross-network pending statuses must come from `BuildPendingStatus` on their service clients; `SessionViewModel` must not switch on those action enums to produce user-visible progress text.

## Current Windows implementation
- `windows/Skybridge.WinClient/ViewModels/FeatureEntryContract.cs` defines the fixed feature entry order.
- `windows/Skybridge.WinClient/ViewModels/SessionViewModel.cs` exposes `NavigationItems`, `SelectedFeature`, session status, top-bar status values from `TopBarStatusClient` using `TopBarStatusSlot`, basic dashboard metrics from `DashboardMetricsClient`, Remote Desktop profile options from `RemoteDesktopProfileCatalogClient`, global session/top-bar action groups from `WorkspaceActionCatalogClient` role IDs, Device Discovery default editable inputs from `DeviceDiscoveryInputDefaultsClient`, Device Discovery scan/browser/manual-target/cross-network-QR-code/parser/pairing/preflight state/results with status/reset/preflight-gate decisions from `ConnectionWorkspaceStateClient`, Smart Connection Code input filtering from `CrossNetworkCodeInputPolicy`, pairing material facts from `PairingMaterialClient`, Device Discovery/Cross-network, `UsbManagementHeaderActions`, `FileTransferHeaderActions`, File Transfer, `RemoteDesktopHeaderActions`, Remote Desktop, `QuantumDiagnosticsHeaderActions`, System Monitor, `SettingsHeaderActions`, and Settings visible action groups from `WorkspaceActionCatalogClient`, File Transfer queue/history/security state/results, Remote Desktop session/control state/results, Quantum/Core diagnostics state/results, System Monitor overview/detail/indicator state/results, Settings tabs/actions/details state/results, and existing connect/heartbeat/disconnect commands.
- `windows/Skybridge.WinClient/MainWindow.xaml` uses the contract as a shell skeleton with left navigation, sidebar session action catalog (`SidebarSessionActions`), top status bar (`TopBarConnectionStatus`, `FPS / Diagnostics`, `TopBarDiagnosticsStatus`, `TopBarActions` for Notifications, Theme, and Heartbeat), dashboard metrics, Device Discovery action catalogs (`DeviceDiscoveryPrimaryActions`, `DeviceDiscoveryScanActions`), `Compatibility Mode`, search, `Manual Host / IP`, `Port` default `11550`, `Code`, `Dynamic Encrypted QR Code`, cross-network QR action catalog (`CrossNetworkQrActions`), QR schema/signature/expiry facts, `Smart Connection Code`, smart-code action catalogs (`CrossNetworkCodePrimaryActions`, `CrossNetworkCodeConnectActions`), service/TXT parser, pairing-code workspace, preflight facts, a USB Management header action catalog (`UsbManagementHeaderActions`) plus stats/device workspace, a File Transfer header/action catalog (`FileTransferHeaderActions`, `FileTransferActions`), a File Transfer queue/history/security workspace, a Remote Desktop header/action catalog (`RemoteDesktopHeaderActions`, `RemoteDesktopActions`), a Remote Desktop session/control workspace, a Quantum/Core diagnostics header catalog (`QuantumDiagnosticsHeaderActions`) and workspace that includes the transport binding digest fact, System Monitor action catalogs (`SystemMonitorHeaderActions`, `SystemMonitorActions`), a System Monitor overview/detail/indicator workspace, Settings action catalogs (`SettingsHeaderActions`, `SettingsToolbarActions`, `SettingsMaintenanceActions`), a Settings tabs/actions/details workspace, selected-feature workspace, and session control action catalog (`SessionControlActions`). Navigation items render through `NavigationItemTemplate`; catalog-backed action surfaces use shared button templates and shared `ItemsPanelTemplate` resources rather than inline per-section button templates, so disabled placeholder actions and future live commands consume the same `WorkspaceActionItemView.Command` / `WorkspaceActionItemView.IsEnabled` contract. Dashboard and USB stat cards use `WorkspaceMetricCardTemplate` and `WorkspaceMetricCardItemsPanel`; read-only facts that share the `Label` / `Value` / `Detail` column contract use `WorkspaceFactRowTemplate` instead of repeated inline row templates across Device Discovery, File Transfer security, Remote Desktop control, Quantum/Core diagnostics, and System Monitor overview/details; System Monitor indicators use `WorkspaceStateRowTemplate` for the matching `Label` / `State` / `Detail` contract; Settings tabs/details/actions use dedicated templates.
- Device Discovery discovered-peer results now use `DiscoveredPeerItemTemplate` rather than an inline `ListView.ItemTemplate`, keeping candidate identity, service, capability, fingerprint, and trust text in one reusable XAML resource.
- USB Management device results, File Transfer queue/history results, and Remote Desktop active-session results now use named item templates (`UsbDeviceItemTemplate`, `FileTransferQueueItemTemplate`, `FileTransferHistoryItemTemplate`, `RemoteDesktopSessionItemTemplate`) instead of inline `ListView.ItemTemplate` blocks.
