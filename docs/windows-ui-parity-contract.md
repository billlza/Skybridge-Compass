# Windows UI parity contract

This contract fixes the Windows shell entry points against the macOS reference so the port can add functionality without drifting from the existing product shape.

## Reference evidence
- macOS navigation order comes from the current TDSC mac branch `origin/tdsc-2026-01-0318-ios-sim-fix:Sources/SkyBridgeCompassApp/Dashboard/Navigation/NavigationItem.swift`: Dashboard, Device Discovery, USB Management, File Transfer, Remote Desktop, Quantum, System Monitor, Settings.
- macOS dashboard routing is implemented in `origin/tdsc-2026-01-0318-ios-sim-fix:Sources/SkyBridgeCompassApp/Dashboard/DashboardView.swift`.
- macOS top bar visible order includes connection state, FPS/diagnostics, notifications, and theme in `origin/tdsc-2026-01-0318-ios-sim-fix:Sources/SkyBridgeCompassApp/Dashboard/TopBar/TopNavigationBarView.swift`; that view also owns the manual connection sheet bindings (`showManualConnectSheet`, IP, port, pairing code), while the visible manual-connect opener may live in the dashboard/device-discovery content surface.
- macOS current-path modularization evidence comes from `origin/tdsc-2026-01-0318-ios-sim-fix:Docs/CoreLayering.md` and handshake reality comes from `origin/tdsc-2026-01-0318-ios-sim-fix:Docs/ProtocolAlignmentPlan.md`; the transport-matrix ADR remains on `origin/tdsc-2026-01-0318-ios-sim-fix-20260211-adr:Docs/ADR-0001-SkyBridge-Core-Transport-Matrix.md`.
- macOS manual connection uses IP Address blank by default, Port `11550`, Pairing Code blank by default, a `Manual Connect` entry point, and a final `Connect` action. The Windows read-only boundary mirrors those fields first, while live connection remains pending behind pairing, trust, Core preflight, and native adapter work.
- macOS cross-network discovery uses `Dynamic Encrypted QR Code` with `Generate QR Code`, `Scan QR Code`, `Waiting for connection...`, `Regenerate`, accepted URI formats `skybridge://connect/<base64url-json>` and `skybridge://connect?data=<base64url-json>`, plus `Smart Connection Code` with `Generate Code`, `Copy`, `Regenerate`, and `Connect`. QR evidence includes `SignedQRPayload`, `DynamicQRCodeData`, `QRCodeSignatureEnvelope`, `QRCodeSignatureQuery`, `sessionID`, `deviceFingerprint`, `publicKey`, `signingPublicKey`, `signature`, `signatureTimestamp`, `expiresAt`, `sig`, `pk`, `ts`, `fp`, `signatureBase64`, `publicKeyBase64`, `timestamp`, and `publicKeyFingerprint`. The short-code input is exactly 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`.
- macOS feature surfaces also include device discovery modes, file transfer actions/history, remote desktop session controls, system monitoring, settings tabs, security/trust/approval, and menu bar quick actions.

## Windows shell contract
- The Windows side navigation must keep the same feature order as the macOS `NavigationItem` list.
- The first visible viewport must be the product workspace, not a landing page. The shell is left navigation, top status/action bar, and main workspace.
- The top bar must surface the selected feature, Core status, connection status, FPS/diagnostics, notifications, theme, and Windows connection controls from the shared session view model. `TopBarStatusClient` is the replaceable read-only boundary for connection/FPS/notification/theme status values so the XAML keeps mac-parity positions while providers remain modular. Manual connection remains a Device Discovery entry point until the mac opener location is fully readable from the TDSC partial clone; Windows must still keep the IP, port, pairing-code, `Manual Connect`, and final `Connect` fields visible in their verified Device Discovery order. Network/IP/speed/latency indicators are optional on macOS settings and may remain provider-pending on Windows, but connection/FPS/notification/theme positions must stay visible and ordered.
- Unimplemented feature pages may show a disabled or placeholder workspace, but their navigation entry must remain present so parity gaps are visible and testable. Device Discovery is no longer a pure placeholder: it has mac-parity scan controls, a read-only Windows DNS-SD browser boundary, a manual target row (`Manual Host / IP`, `Port`, `Code`, `Manual Connect`), cross-network QR/code controls (`Dynamic Encrypted QR Code`, `Generate QR Code`, `Scan QR Code`, `Smart Connection Code`, `Generate Code`, `Copy`, `Regenerate`, `Connect`), a manual Core-validated Bonjour service/TXT parser, a pairing-code validator, and a `Prepare Connection` preflight view while real DNS-SD browsing, trust-store persistence, signaling, and native adapter launch remain pending.
- Device Discovery scan controls must stay in the same functional order as the TDSC mac local-scan surface where practical: compatibility mode, extended search, manual connect, start/stop scan, refresh, search, then manual target fields and device list/results. Windows may keep manual target/TXT/pairing/preflight controls visible while native DNS-SD and trust persistence are pending, but it must not hide or reorder the scan/search/refresh/start/stop entry points.
- USB Management must keep the macOS device-management shape visible: refresh, last scan, MFi certified count, Android device count, storage device count, total device count, empty state, device list, device ID, vendor ID, product ID, serial number, connection interface, and capabilities. Until Windows USB providers are wired, MFi/Android/vendor/product/serial details must be labeled pending instead of synthesized.
- File Transfer must keep the macOS quick-action shape visible: select files, select folder, QR sharing, transfer queue, transfer history, HMAC, and signature status. Until the real file picker and transport are wired, those actions may remain disabled but the queue/history/security workspace must be driven by Core contracts.
- Remote Desktop must keep the macOS session shape visible: recommended connect, advanced connect, connection mode, active/recent sessions, performance overlay, quality controls, settings, fullscreen, and disconnect. Until live capture/input/video transport are wired, those actions may remain disabled but the session/control workspace must be driven by Core contracts.
- System Monitor must keep the macOS monitoring shape visible: monitoring status, stop monitoring, advanced/helper monitoring, overview metrics, detailed monitoring cards, health, thermal, and load indicators. Until ETW/GPU/thermal providers are wired, unsupported metrics must be labeled pending instead of synthesized.
- Settings must keep the macOS preference-workspace shape visible: General, Network, Devices, File Transfer, Remote Desktop, System Monitor, Permissions, and Advanced tabs; export/import/reset actions; permission/system-settings actions; apply/default/reset-monitor actions; File Transfer, Video Transfer, Remote Desktop, System Monitor, and PQC/Core policy fields. Until persistence and providers are wired, high-risk writes must stay disabled and separated from read-only refresh.
- Connection, heartbeat, and disconnect commands must stay bound to `SessionViewModel` and must not invent per-page state.
- Runtime protocol facts must come from Rust Core contracts: transport selection, transport binding digest, channel mapping, connection planning, suite selection, frame metadata, and engine diagnostics. Pairing public keys must come from validated pairing material, not discovery `pubKeyFP`. Device Discovery browser facts must come from `WindowsDiscoveryBrowserClient`, which is the replaceable Win32 `DnsServiceBrowse` boundary and feeds candidates through `CoreDiscoveryClient`; it must not synthesize trusted peers. Manual target facts must come from `ManualConnectionClient`; host/port/code input may create only a read-only `_skybridge._tcp` target snapshot, and the code must never be treated as a peer public key. Cross-network QR/code facts must come from `CrossNetworkConnectionClient`; QR/code input may create only a read-only schema/signature/expiry snapshot for `SignedQRPayload`, `DynamicQRCodeData`, `QRCodeSignatureEnvelope`, or `QRCodeSignatureQuery`, and Windows must report `CrossNetworkReadiness` as `idle` until the dynamic QR canonical verifier, trust approval, signaling, Core planning, and transport binding are wired. Device Discovery preflight must call `ConnectionPreflightClient` over `CoreBridge.PlanConnectionAsync`, `CoreBridge.ComputeTransportBindingDigestAsync`, and channel mapping before any real adapter launch is enabled. Quantum/Core diagnostics must call `CoreDiagnosticsClient` over `CoreBridge`, including `CoreBridge.ComputeTransportBindingDigestAsync`, not re-derive protocol state in XAML or view-model code.

## Current Windows implementation
- `windows/Skybridge.WinClient/ViewModels/FeatureEntryContract.cs` defines the fixed feature entry order.
- `windows/Skybridge.WinClient/ViewModels/SessionViewModel.cs` exposes `NavigationItems`, `SelectedFeature`, session status, top-bar status values from `TopBarStatusClient`, basic dashboard metrics from `DashboardMetricsClient`, Device Discovery scan/browser/manual-target/cross-network-QR-code/parser/pairing/preflight state/results, USB Management stats/device state/results, File Transfer queue/history/security state/results, Remote Desktop session/control state/results, Quantum/Core diagnostics state/results, System Monitor overview/detail/indicator state/results, Settings tabs/actions/details state/results, and existing connect/heartbeat/disconnect commands.
- `windows/Skybridge.WinClient/MainWindow.xaml` uses the contract as a shell skeleton with left navigation, top status bar (`TopBarConnectionStatus`, `FPS / Diagnostics`, `TopBarDiagnosticsStatus`, `Notifications`, `TopBarNotificationsStatus`, `Theme`, `TopBarThemeStatus`, `Heartbeat`), dashboard metrics, Device Discovery `Compatibility Mode`, `Extended Search`, `Manual Connect`, `Start Scan`, `Stop Scan`, `Refresh`, search, `Manual Host / IP`, `Port` default `11550`, `Code`, `Dynamic Encrypted QR Code`, `Generate QR Code`, `Scan QR Code`, QR schema/signature/expiry facts, `Smart Connection Code`, `Generate Code`, `Copy`, `Regenerate`, `Connect`, service/TXT parser, pairing-code workspace, `Prepare Connection` preflight facts, a USB Management stats/device workspace, a File Transfer queue/history/security workspace, a Remote Desktop session/control workspace, a Quantum/Core diagnostics workspace that includes the transport binding digest fact, a System Monitor overview/detail/indicator workspace, a Settings tabs/actions/details workspace, selected-feature workspace, and session controls.

## Acceptance checks to add
- Static test: run `Scripts/verify-windows-ui-parity.ps1` to verify `FeatureEntryContract.Entries` matches the macOS navigation IDs and order, and that the shell exposes the required ordered dashboard metrics from `DashboardMetricsClient`, ordered top-bar actions from `TopBarStatusClient`, ordered workspace sections, ordered Device Discovery scan/browser/manual-target/cross-network-QR-code schema/signature/expiry/parser/pairing/connection-preflight signals, ordered USB Management/File Transfer/Remote Desktop/Settings action signals, Quantum/Core diagnostics signals including transport binding digest visibility, System Monitor overview/detail/indicator signals, Settings tabs/actions/details signals, and commands.
- UI automation: each navigation entry can be selected and updates the selected-feature heading.
- UI automation: connect, heartbeat, and disconnect buttons enable/disable according to `EngineConnectionState`.
- Visual QA: left navigation order, feature/action order, top status bar, metric row, and session controls remain in stable positions across desktop window sizes.
- Diagnostic UI: expose `CoreBridge.PlanConnectionAsync`, transport selection, transport binding digest, channel mapping, frame codec metadata, suite negotiation, engine snapshot, metrics, and event queue output without silent fallback. Device Discovery manual target, cross-network QR/code schema/signature/expiry snapshot, and preflight should state that no connection attempt is started and that `FfiEngineClient` remains behind explicit native DLL deployment.
