# Windows UI parity contract

This contract fixes the Windows shell entry points against the macOS reference so the port can add functionality without drifting from the existing product shape.

## Reference evidence
- macOS navigation order comes from pinned TDSC commit `23ba06343bbaa58c30ef6b9bbddd09bb4e80241c:Sources/SkyBridgeCompassApp/Dashboard/Navigation/NavigationItem.swift`: Dashboard, Device Discovery, USB Management, File Transfer, Remote Desktop, Quantum, System Monitor, Settings.
- macOS dashboard routing is implemented in pinned TDSC commit `23ba06343bbaa58c30ef6b9bbddd09bb4e80241c:Sources/SkyBridgeCompassApp/Dashboard/DashboardView.swift`; its `mainContent` switches on `selectedNavigation`, so only the selected feature workspace renders in the main content area.
- macOS dashboard default content is implemented in pinned TDSC commit `23ba06343bbaa58c30ef6b9bbddd09bb4e80241c:Sources/SkyBridgeCompassApp/Dashboard/Sections/DashboardContentView.swift`; it renders overview stats followed by panel entry points for device discovery, remote sessions, quick actions, weather, and Apple Silicon/Core info. The quick-action evidence in `23ba06343bbaa58c30ef6b9bbddd09bb4e80241c:Sources/SkyBridgeCompassApp/Dashboard/Sections/QuickActionsPanelView.swift` fixes the visible order as Scan Devices, File Transfer, System Monitor, and Settings.
- macOS top bar visible order includes connection state, FPS/diagnostics, notifications, and theme in pinned TDSC commit `23ba06343bbaa58c30ef6b9bbddd09bb4e80241c:Sources/SkyBridgeCompassApp/Dashboard/TopBar/TopNavigationBarView.swift`; that view also owns the manual connection sheet bindings (`showManualConnectSheet`, IP, port, pairing code), while the visible manual-connect opener may live in the dashboard/device-discovery content surface.
- macOS current-path modularization evidence comes from `origin/tdsc-2026-01-0318-ios-sim-fix:Docs/CoreLayering.md` and handshake reality comes from `origin/tdsc-2026-01-0318-ios-sim-fix:Docs/ProtocolAlignmentPlan.md`; the transport-matrix ADR remains on `origin/tdsc-2026-01-0318-ios-sim-fix-20260211-adr:Docs/ADR-0001-SkyBridge-Core-Transport-Matrix.md`.
- macOS manual connection uses IP Address blank by default, Port `11550`, Pairing Code blank by default, a `Manual Connect` entry point, and final `Cancel` / `Connect` actions. The Windows read-only boundary mirrors those fields first; `Cancel` clears prepared manual-target facts without starting transport, while live connection remains pending behind pairing, trust, Core preflight, and native adapter work.
- Windows production defaults must mirror those empty mac manual/discovery inputs: keep `_skybridge._udp` and port `11550`, but leave Bonjour TXT and pairing-code fields blank unless a user or explicit test fixture supplies material.
- macOS cross-network discovery uses `Dynamic Encrypted QR Code` with `Generate QR Code`, `Scan QR Code`, `Waiting for connection...`, `Regenerate`, accepted URI formats `skybridge://connect/<base64url-json>` and `skybridge://connect?data=<base64url-json>`, plus `Smart Connection Code` with `Generate Code`, `Copy`, `Regenerate`, and `Connect`. QR evidence includes `SignedQRPayload`, `DynamicQRCodeData`, `QRCodeSignatureEnvelope`, `QRCodeSignatureQuery`, `sessionID`, `deviceFingerprint`, `publicKey`, `signingPublicKey`, `signature`, `signatureTimestamp`, `expiresAt`, `sig`, `pk`, `ts`, `fp`, `signatureBase64`, `publicKeyBase64`, `timestamp`, and `publicKeyFingerprint`. The short-code input is exactly 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`.
- macOS feature surfaces also include device discovery modes, file transfer actions/history, remote desktop session controls, system monitoring, settings tabs, security/trust/approval, and menu bar quick actions.

## Windows shell contract
- The Windows side navigation must keep the same feature order as the macOS `NavigationItem` list, and its glyph/title/status row must render through `NavigationItemTemplate` so the primary product entry points stay testable outside inline ListView markup.
- The first visible viewport must be the product workspace, not a landing page. The shell is left navigation, top status/action bar, and main workspace.
- The main workspace feature sections must keep the macOS/TDSC source order in XAML for static parity review, but runtime visibility must match the macOS `mainContent` switch: Dashboard, Device Discovery, USB Management, File Transfer, Remote Desktop, Quantum/Core Diagnostics, System Monitor, and Settings are gated by selected-feature booleans through `BoolToVisibilityConverter`. Dashboard's default workspace must show overview metrics first, then the mac quick-action entry points in order: Scan Devices, File Transfer, System Monitor, Settings. Persistent Windows session controls may remain visible below the selected feature workspace because they are global session controls, not a replacement feature page.
- The top bar must surface the selected feature, Core status, connection status, FPS/diagnostics, notifications, theme, and Windows connection controls from the shared session view model. `TopBarStatusClient` is the replaceable read-only boundary for connection/FPS/notification/theme status values, resolved status snapshots, action-detail snapshots, slot lookup, and notification/theme defaults, `TopBarStatusSlot` is the stable scalar mapping key, and `WorkspaceActionCatalogClient` owns the ordered global session/top-bar/action catalogs (`SidebarSessionActions`, `TopBarActions`, `SessionControlActions`, `DashboardQuickActions`), initial surface load order, dynamic surface refresh order, plus stable `WorkspaceActionCommandId`, `WorkspaceActionGateId`, and `WorkspaceActionDetailSlot` roles so the XAML keeps mac-parity positions while providers remain modular. All catalog-backed buttons must render through shared XAML resources (`WorkspaceActionButtonTemplate`, `WorkspaceActionButtonWithDetailTemplate`, `SidebarWorkspaceActionButtonTemplate`, `DashboardQuickActionTemplate`, and the shared action `ItemsPanelTemplate` resources) so title-bar, toolbar, quick-action, and session-control positions share one style and one `IsEnabled` binding path. Repeated `Title` / `Value` / `Detail` metric cards must render through `WorkspaceMetricCardTemplate` and `WorkspaceMetricCardItemsPanel`, starting with Dashboard metrics and USB Management stats; Dashboard metric values must come from `DashboardMetricsClient.Metrics`, while the scalar status properties remain available for status/top-bar logic. Repeated read-only `Label` / `Value` / `Detail` fact rows must render through `WorkspaceFactRowTemplate` when they share the same column contract, including Device Discovery browser/manual/cross-network/pairing/preflight facts plus File Transfer security, Remote Desktop control, Quantum/Core diagnostic, and System Monitor overview/detail facts. Repeated `Label` / `State` / `Detail` indicator rows must render through `WorkspaceStateRowTemplate`, starting with System Monitor health/thermal/load indicators. Settings tab `Title` / `Detail` rows must render through `SettingsTabItemTemplate`; Settings four-column `Section` / `Label` / `Value` / `Detail` rows must render through `SettingsDetailRowTemplate`, and four-column `Key` / `Title` / `State` / `Detail` rows must render through `SettingsActionRowTemplate`. Manual connection remains a Device Discovery entry point until the mac opener location is fully readable from the TDSC partial clone; Windows must still keep the IP, port, pairing-code, `Manual Connect`, and final `Cancel` / `Connect` fields visible in their verified Device Discovery order. Network/IP/speed/latency indicators are optional on macOS settings and may remain provider-pending on Windows, but connection/FPS/notification/theme positions must stay visible and ordered.
- Top-bar status slot containers must expose stable UI automation ids (`Skybridge.TopBar.ConnectionStatus`, `Skybridge.TopBar.DiagnosticsStatus`, and `Skybridge.Actions.TopBar`) so parity tests can assert their visible positions independently of localized text or runtime values.
- `TopBarActions` must expose the mac top-bar notification and theme positions only; heartbeat remains available through sidebar/session controls so it does not shift the notification/theme slots. `Notifications` must resolve through `WorkspaceActionCommandId.OpenTopBarNotifications` plus `WorkspaceActionGateId.CanOpenTopBarNotifications`, and `Theme` must resolve through `WorkspaceActionCommandId.ToggleTopBarTheme` plus `WorkspaceActionGateId.CanToggleTopBarTheme`, with readiness from `ITopBarStatusClient` and execution through `TopBarWorkspaceActions`. Until notification center and permission prompt providers are wired, `Notifications` must return a service-owned fail-closed status message without opening permission UI. `Theme` may cycle the top-bar status through an explicit in-memory provider (`System` / `Dark` / `Light`) for mac-parity button behavior, but Windows system theme mutation and persisted preference writes must stay disabled until Settings owns those provider bridges.
- `DashboardQuickActions` must expose Scan Devices, File Transfer, System Monitor, and Settings in that order through `WorkspaceActionSurface.DashboardQuickActions`. The current Windows behavior is navigation-only through `DashboardNavigationActions`; it must not start discovery, file transfer, monitoring, settings writes, FFI, WebRTC, signaling, or adapter work from the dashboard surface.
- Device Discovery discovered-peer rows must render through `DiscoveredPeerItemTemplate` so mac/iOS candidates keep one testable `DisplayName` / `DeviceId` / `Platform` / `ServiceKind` / `CapabilitiesSummary` / `PublicKeyFingerprint` / `TrustSummary` layout outside inline `ListView.ItemTemplate` markup.
- USB device rows, File Transfer queue/history rows, and Remote Desktop session rows must render through `UsbDeviceItemTemplate`, `FileTransferQueueItemTemplate`, `FileTransferHistoryItemTemplate`, and `RemoteDesktopSessionItemTemplate`; `MainWindow.xaml` must not define inline `ListView.ItemTemplate` blocks for these mac-parity workspaces.
- Unimplemented feature pages may show a disabled or placeholder workspace, but their navigation entry must remain present so parity gaps are visible and testable. Device Discovery is no longer a pure placeholder: it has mac-parity scan controls, a read-only Windows DNS-SD browser boundary, default editable input values from `DeviceDiscoveryInputDefaultsClient`, a manual target row (`Manual Host / IP`, `Port`, `Code`, `Manual Connect`), visible final manual `Cancel` / `Connect` slots, cross-network QR/code controls (`Dynamic Encrypted QR Code`, `Generate QR Code`, `Scan QR Code`, `Smart Connection Code`, `Generate Code`, `Copy`, `Regenerate`, `Connect`), a manual Core-validated Bonjour service/TXT parser, a pairing-code validator, and a `Prepare Connection` preflight view while real DNS-SD browsing, trust-store persistence, signaling, and native adapter launch remain pending. `WorkspaceActionCatalogClient` owns the ordered visible Device Discovery and cross-network command groups plus their command role IDs (`Parse TXT`, `Validate Pairing`, `Prepare Connection`; `Extended Search`, `Manual Connect`, final manual `Cancel`, final manual `Connect`, `Start Scan`, `Stop Scan`, `Refresh`; `Generate QR Code`, `Scan QR Code`; `Generate Code`, `Copy`, `Regenerate`, `Connect`) while `SessionViewModel` keeps the actual command objects and readiness gates.
- Device Discovery scan controls must stay in the same functional order as the TDSC mac local-scan surface where practical: compatibility mode, extended search, manual connect, start/stop scan, refresh, search, then manual target fields and device list/results. Windows may keep manual target/TXT/pairing/preflight controls visible while native DNS-SD and trust persistence are pending, but it must not hide or reorder the scan/search/refresh/start/stop entry points. The Device Discovery final `Cancel` slot must bind to `WorkspaceActionCommandId.CancelManualConnection` plus `WorkspaceActionGateId.CanUseDiscoveryBrowser` and only clear manual-target preparation state; the final `Connect` slot must bind to the same `WorkspaceActionCommandId.Connect` and `WorkspaceActionGateId.CanConnect` roles as Sidebar and Session Controls so it has the mac-parity position without inventing a page-local connection path.
- Smart Connection Code `Connect` must keep the mac-parity action visible while remaining an explicit envelope-validation step until signaling/trust/adapter work is ready. Its pending status is `Validating code...`, a valid six-character input produces `Code envelope validated` with `CrossNetworkReadiness=idle`, invalid inputs fail closed, and the facts must say no WebRTC join, signaling room join, HTTP file server, or `FfiEngineClient` launch is started.
- USB Management must keep the macOS device-management shape visible: refresh, last scan, MFi certified count, Android device count, storage device count, total device count, empty state, device list, device ID, vendor ID, product ID, serial number, connection interface, and capabilities. `WorkspaceActionCatalogClient` owns `UsbManagementHeaderActions` (`Refresh Devices`) so the header button position remains testable outside XAML. Until Windows USB providers are wired, MFi/Android/vendor/product/serial details must be labeled pending instead of synthesized.
- File Transfer must keep the macOS quick-action shape visible: refresh plan, select files, select folder, QR sharing, transfer queue, transfer history, HMAC, and signature status. `WorkspaceActionCatalogClient` owns `FileTransferHeaderActions` (`Refresh Plan`) and the ordered quick-action catalog (`Select Files`, `Select Folder`, `Generate QR`) so button position remains testable outside XAML. `Generate QR` must resolve through `WorkspaceActionCommandId.GenerateFileTransferQr` plus `WorkspaceActionGateId.CanGenerateFileTransferQr`, with readiness coming from `IFileTransferWorkspaceClient.CanGenerateShareQr`; until real QR sharing is wired it must remain fail-closed without reading files, opening signaling, or starting transport. Until the real file picker is wired, `Select Files` and `Select Folder` may remain disabled, but the queue/history/security workspace must be driven by Core contracts.
- `Select Files` and `Select Folder` must also be command-backed instead of fixed catalog booleans: `Select Files` resolves through `WorkspaceActionCommandId.SelectFileTransferFiles` plus `WorkspaceActionGateId.CanSelectFileTransferFiles` with readiness from `IFileTransferWorkspaceClient.CanSelectFiles`, and `Select Folder` resolves through `WorkspaceActionCommandId.SelectFileTransferFolder` plus `WorkspaceActionGateId.CanSelectFileTransferFolder` with readiness from `IFileTransferWorkspaceClient.CanSelectFolder`. Default selection actions may prepare in-memory intents through `IFileTransferSelectionIntentClient`, but until native picker/manifest support is wired, they must not open a picker, scan a directory, read local files, or create a transfer manifest.
- Remote Desktop must keep the macOS session shape visible: refresh sessions, recommended connect, advanced connect, connection mode, active/recent sessions, performance overlay, quality controls, settings, fullscreen, and disconnect. `RemoteDesktopProfileCatalogClient` owns the shared bitrate/framerate profile options, defaults, and selection-status text used by both the Remote Desktop workspace and Session Controls, while `WorkspaceActionCatalogClient` owns `RemoteDesktopHeaderActions` (`Refresh Sessions`) and the ordered Remote Desktop quick-action catalog (`Recommended Connect`, `Advanced Connect`, `Performance Overlay`, `Quality`, `Settings`, `Full Screen`, `Disconnect Session`) so button position remains testable outside XAML. Until live capture/input/video transport are wired, those actions may remain disabled but the session/control workspace must be driven by Core contracts.
- Each Remote Desktop quick action must be command-backed instead of a fixed catalog boolean: `Recommended Connect`, `Advanced Connect`, `Performance Overlay`, `Quality`, `Settings`, `Full Screen`, and `Disconnect Session` resolve through their `WorkspaceActionCommandId` / `WorkspaceActionGateId` pairs, with readiness from `IRemoteDesktopWorkspaceClient`. Until live remote-control support is wired, `Recommended Connect`, `Advanced Connect`, `Full Screen`, and `Disconnect Session` must return service-owned fail-closed status facts without starting capture, forwarding input, launching transport, opening windows, or disconnecting a peer. `Performance Overlay`, `Quality`, and `Settings` may update an explicit in-memory `IRemoteDesktopControlPanelClient` so the mac-parity controls are usable without starting overlay windows, telemetry samplers, encoder changes, runtime preference writes, or transport.
- Quantum/Core Diagnostics must keep the Core-owned protocol facts visible behind an explicit header action. `WorkspaceActionCatalogClient` owns `QuantumDiagnosticsHeaderActions` (`Run Diagnostics`) while `CoreDiagnosticsClient` owns transport binding digest, suite, SBP2, channel, and frame facts; running diagnostics must not initiate a session.
- System Monitor must keep the macOS monitoring shape visible: refresh metrics, monitoring status, stop monitoring, advanced/helper monitoring, overview metrics, detailed monitoring cards, health, thermal, and load indicators. `WorkspaceActionCatalogClient` owns the ordered System Monitor header/control catalogs (`Refresh Metrics`; `Monitoring`, `Stop Monitoring`, `Enable Advanced Monitoring`) so button positions remain testable outside XAML. ## Current Windows implementation
- `windows/Skybridge.WinClient/Services/FeatureCatalogClient.cs` defines the fixed feature entry order and default selected entry.
- `windows/Skybridge.WinClient/SessionViewModelDependencyFactory.cs` owns the Windows runtime service graph selector, and `SessionViewModelDependencies` carries that graph into `SessionViewModel`; `MainWindow.xaml.cs` must call `SessionViewModelDependencyFactory.CreateConfigured()` rather than directly constructing `CoreBridge` or concrete service clients. `CreateDefault()` remains the safe product default with `DummyEngineClient`, pending DNS-SD, and pending transport adapters. `WindowsNativeRuntimeDependencyFactory` may select `FfiEngineClient`, `NativeWindowsDnsSdBrowseClient`, an external transport adapter, or the verified WebRTC helper-proof adapter only after explicit `SKYBRIDGE_WINDOWS_RUNTIME=native` environment configuration; the external profile must consume required endpoint/candidate/digest variables, optional `SKYBRIDGE_WINDOWS_RELAY_ID`, optional `SKYBRIDGE_WINDOWS_ADAPTER_KIND`, and positive `SKYBRIDGE_WINDOWS_TIMESTAMP_WINDOW_MS`, while `SKYBRIDGE_WINDOWS_TRANSPORT_ADAPTER=webrtc-verified` must consume `SKYBRIDGE_WINDOWS_WEBRTC_PROOF_PATH`, positive `SKYBRIDGE_WINDOWS_WEBRTC_PROOF_MAX_AGE_MS` when provided, a fresh DataChannel-open/SBF1-echo proof, and must not allow Windows to claim AppleNative.
- `windows/Skybridge.WinClient/Skybridge.WinClient.csproj` targets `net10.0-windows10.0.19041.0` with `WindowsPackageType=None`, `Microsoft.WindowsAppSDK` `2.1.3`, and `Microsoft.Windows.SDK.BuildTools` `10.0.28000.1839`; the BuildTools pin must stay aligned with the current stable Windows SDK NuGet package so restore does not drift back to an older 26100 build, and `WindowsPackageType=None` must stay present so the unpackaged WinUI process auto-initializes the Windows App SDK runtime before `Application.Start`.
- `windows/Skybridge.WinClient/MainWindow.xaml` keeps shared templates and item-panel resources in the root `Grid.Resources`; `Window.Resources` must not return because it fails WinUI XAML compilation on the current Windows App SDK stack. `MainWindow.xaml.cs` assigns `RootShell.DataContext = ViewModel` because WinUI `Window` does not expose the WPF-style `DataContext` property.
