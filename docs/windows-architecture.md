# Skybridge Windows client architecture

The WinUI client is organized to keep UI binding, engine integration, and platform FFI clearly separated so the Rust core can be slotted in without disrupting the shell.

## Q-Periapt native primitive boundary

The existing `skybridge_core` library links Q-Periapt 0.1.5 ABI 2 from the exact official source revision `7ed1f96a7ec33732f02a989dd5a4669cdcce39ad`. `Cargo.lock` binds its resolved dependency graph, and `NativeCore.targets` builds with `--locked`. The client ships one Core library; no separate Q DLL or alternative handshake implementation is introduced.

The vendored C sources use UTF-8. The repository-root `.cargo/config.toml` gives the existing x86, x64 and ARM64 Windows MSVC targets a `/utf-8` default through their target-specific `CFLAGS` variables. This declares source encoding while retaining C11 and the existing `/W4` and `/WX` checks; it does not change the machine code page. Direct Cargo commands run from `core/skybridge-core` discover this file, and `NativeCore.targets` explicitly selects the same file with `--config`. The MSBuild command keeps its working directory and output-directory rules, including relative `SkybridgeCoreTargetDir` overrides.

The defaults use `force = false`. The pinned `cc` version appends target-specific flags after generic `CFLAGS`, so existing generic flags are retained. An existing same-name target environment variable is an explicit complete override and must itself retain `/utf-8` or an equivalent UTF-8 source declaration for the selected compiler. A higher-priority hyphenated target variable can also override conflicting flags. These defaults are for MSVC-style compiler drivers; selecting a different driver requires compatible target flags. Linux, macOS and Windows GNU targets do not consume these MSVC target defaults. No global environment or SDK source change is required.

`CoreBridge.QPeriapt` exposes five metadata functions and four caller-buffer operations: signed-policy resolution, key generation, encapsulation and decapsulation. Each operation preserves the native parameter order and signed status code. Managed lengths come from the actual arrays. ABI 2 uses a 40-byte decision value, not an allocated native context handle. Core initialization checks the ABI, version, fixed suite and status names before accepting the native library.

The internal `QPeriaptNativeClient` verifies an independently provisioned SHA-256 pin for the policy verification key, copies operation inputs, checks fixed buffer sizes, and reuses `ProductHandshakeSharedSecret` for secret ownership. A key owner has a short snapshot/commit/dispose lock; native computation runs outside it. A disposed owner cannot publish a late result. Native execution is synchronous and cannot be interrupted by a managed cancellation token: cancellation before admission or at result publication is explicit, and unpublished secret buffers are erased.

The trusted policy head is exactly 36 bytes: a big-endian version followed by SHA3-256 of the exact signed policy. The schema 1 public material historically names that digest `policy_digest_sha256_hex`; its authenticated native value remains SHA3-256. The product embeds the shared production policy and independently pins its ML-DSA-65 verification key. `QPeriaptRuntimeSession.Prepare` verifies the signed policy, commits the head through `QPeriaptTrustedStateStore`, and runs the native KEM probe before exposing a session. The store uses the existing DPAPI and atomic file-commit boundaries with an exclusive compare-and-swap lease. A primitive decision or KEM operation alone is not product peer authentication.

The existing LAN identity owner adds Q material through a schema 1 to schema 2 upgrade while retaining the device ID, ML-DSA key, original ML-KEM key, and all peer authorizations. A complete, immutable schema 1 preimage is committed before replacing the identity. The original fixed backup is never overwritten. If an older App legitimately changes schema 1 after rollback, the owner validates that prior backup with the same strict schema, key-pair and trusted-peer checks, requires the same device/signing/legacy KEM identity, and keeps the new complete ciphertext under a deterministic independent snapshot name. SHA256 is used only for ciphertext snapshot naming and idempotent deduplication; exact byte comparison and the existing identity validation remain mandatory. Snapshot creation uses a same-directory flushed temporary file and atomic no-replace commit, without scanning prior snapshots or merging archived permissions. Its separate policy head survives an explicit identity rollback. If the policy head commits before an interrupted identity write, retry uses the existing enrollment; an enrolled schema 2 identity with a missing or damaged head fails closed. A damaged schema 2 identity is never replaced automatically by its preimage. The `--native-policybound-reupgrade <frozen-legacy-contract-assembly>` profile executes the archived schema 1 product owner in an isolated process to add a pairing after rollback, then exercises real snapshot-commit termination, idempotent re-upgrade and corrupt/conflicting/write-failure rejection. The archived owner fixture does not enter the product package.

A peer with only its existing ML-KEM authority keeps the existing `0x0102` selection. An explicitly imported Q key preserves the same signing identity and legacy key and enables `0x0012`; network discovery alone cannot replace trusted material. The shared provider and MessageA/MessageB/FIN1 core implement the exact Apple/Android policy-bound context, 1216-byte public key, 3648-byte expanded private representation, and 1120-byte ciphertext. Suite `0x0012` retains `v1-single` and an empty responder share. The extra forward-secret contribution belongs only to `0x0102`; the suites do not claim equivalent forward-secrecy properties. Errors after Q selection never trigger suite fallback.

Windows emits its actual kernel version as `Windows 10.0.<build>` and requires the existing minimum build 19041 plus native ML-DSA/ML-KEM availability, ABI admission, signed-policy verification, durable state, and a successful native probe. Metadata alone does not prove native capability. The environment-configured WebRTC composition and the current-path connector retain their existing separate readiness gates; this change does not supply a cross-NAT UI or a new credential mechanism.

## Current native LAN product paths — 2026-09-09

`WindowsDeviceWorkspace` extends the existing remote-control identity owner in place. Its stored directory, keys, trust records and schema are unchanged. It now owns up to eight admitted LAN control sessions as well as the remote-control host/viewer resources. `TcpProductControlTransport` and `ProductPeerAuthentication` are the renamed shared carrier and authentication preparation; remote-control frame bounds remain unchanged.

File transfer uses resolved `_skybridge._tcp` control and `_skybridge-xfer._tcp` file routes with matching canonical device identity, fingerprint, host and provenance. The selected authenticated product handshake (0x0102 for an existing legacy peer, 0x0012 for an explicitly enrolled Q peer), identity exchange and ordered ping admission precede file-key authorization. Remote-control keys are not used as substitutes for a classic file-transfer control session.

The `Services/FileTransfer` workers implement the established classic v2 metadata/chunk/completion/receipt contract, bounded AES-GCM chunks and existing authenticated transcripts. Apple's `compression=zlib` mode means raw RFC 1951 DEFLATE from Foundation/COMPRESSION_ZLIB; Windows uses `DeflateStream` and an Apple-produced fixed vector. It must not guess between compressed formats or weaken authentication/output limits. See [Apple's format definition](https://developer.apple.com/documentation/compression/compression_zlib).

A source descriptor and full digest are prepared before opening the receiver's short initial-frame deadline. The receiver has at most two workers, requires current peer admission and explicit approval, and writes to a private staging file before atomic non-overwrite completion. The approval prompt and disk commit share one immutable destination snapshot; a new connection adopts changed receive-directory settings. File success requires the receiver's authenticated complete byte count and digest, not a closed socket. Committed files survive a receipt-delivery error.

Selection supports up to 64 files or one folder; a folder is sent as a bounded ZIP without automatic extraction. The classic file-size limit is 2 GiB. Active operations are cancelled and drained on disconnect/shutdown, and real transfer work holds a system-only power request. History is bounded to 100 entries in memory. Transfer resume and share QR are not advertised. Generic cross-network and engine connection controls retain their own readiness boundaries.

Native builds, contract tests and file receipts have been collected independently. Visible input and UI acceptance requires an unlocked desktop; background UI Automation and SSH access alone do not satisfy that gate. Mac/iOS and Android regression must be tracked against their own current devices and artifacts.

## ADR alignment
- The current cross-platform contracts are Apple project `Docs/ADR-0001-SkyBridge-Core-Transport-Matrix.md` (version 1.1, reviewed 2026-09-08) and `Docs/ADR-0002-Remote-Control-Authority-and-Sessions.md`. Their target architecture, implementation status, and device acceptance are separate gates.
- `SkyBridgeProtocolCore` owns shared contracts without platform UI or networking dependencies; Apple transport implementations remain in `SkyBridgeAppleTransport`. Windows platform adapters consume the same identity, handshake, channel and input-lease semantics.
- The binary product handshake remains the only handshake wire. Authenticated application messages may be JSON, but must not become a second JSON handshake or identity system.
- WebRTC, MsQuic and Apple Network.framework are transport adapters. Shared protocol ownership and current implementation evidence take precedence over historical paper claims.
- `Docs/CrossPlatformDiscoveryDesign.md` on the current TDSC branch is a 2026-01-11 draft and is lower precedence than the ADR, current code, and Microsoft API guidance. Its Windows Bonjour SDK recommendation is retained only as historical context; the Windows implementation plan follows the replaceable Win32 DNS-SD boundary below.
- Windows-to-Windows retains the native MsQuic target. Apple interoperability preserves compatible authenticated LAN paths; WebRTC is the cross-NAT adapter. Apple-to-Apple remains on its native transport path. Existing generic transport readiness gates are not proof that a native product entry is wired.
- Windows MsQuic dial, listen, and transport-secret binding consume the single C# protocol source `SkyBridgeProtocolConstants.MsQuicAlpn`, whose ADR value is `skybridge-sbq/1`. `WindowsNativeMsQuicTransportSecret.Derive` rejects an empty, differently cased, or otherwise mismatched negotiated ALPN before producing binding material.
- Apple-compatible discovery uses `_skybridge._udp` / `_skybridge._tcp` for control and `_skybridge-xfer._tcp` / `_skybridge-rd._tcp` as the canonical file-transfer / remote-desktop service names. `_skybridge-transfer._tcp` and `_skybridge-remote._tcp` remain input-only compatibility aliases. `discovery.rs` accepts both spellings but `DiscoveryServiceKind.service_type()` emits only canonical names; Windows resolved endpoints and authenticated route bindings likewise canonicalize service and instance names before projection or storage. TXT fields remain `deviceId`, `pubKeyFP`, `platform`, `capabilities`, `name`, and `version`, and `skybridge_parse_discovery_advertisement` / `CoreBridge.ParseDiscoveryAdvertisementAsync` expose the same parser to Windows DNS-SD or pairing services.
- The TDSC mac top-bar manual connection surface keeps IP Address blank by default, Port at `11550`, and Pairing Code blank. Its manual path constructs an `_skybridge._tcp` target only after user input, so Windows must mirror those fields without treating a typed code as a trusted peer key or bypassing discovery/pairing/trust checks.
- Windows production defaults keep Bonjour TXT and pairing-code inputs blank; sample mac advertisements and `skybridge-pair:v1` material belong in tests or explicit developer fixtures, not startup UI state.
- The TDSC mac cross-network connection surface includes `Dynamic Encrypted QR Code` and `Smart Connection Code`: QR uses `skybridge://connect/<base64url-json>` and scan accepts `skybridge://connect?data=<base64url-json>`. The current mac QR payloads include `DynamicQRCodeData` (`version`, `sessionID`, `deviceName`, `deviceFingerprint`, `publicKey`, `signingPublicKey`, `signature`, `signatureTimestamp`, `iceServers`, `expiresAt`), the older `SignedQRPayload` wrapper, and QR signature-test query/envelope forms using `sig`, `pk`, `ts`, `fp`, `signatureBase64`, `publicKeyBase64`, `timestamp`, and `publicKeyFingerprint`. TDSC signs dynamic QR with the `P2PSecurityManager` canonical string `id|name|type|address|port|os|cap|ts|fp`, but the current `DynamicQRCodeData` does not carry the signed `osVersion`, so Windows must treat current dynamic QR bodies as `unverifiable` after schema/key/timestamp/expiry validation. Windows verifies legacy/canonical P256 signatures where the payload contains the full canonical material, and verifies dynamic QR only when a future or supplemental payload supplies the signed OS version needed to rebuild that canonical string. Smart codes are 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, show `Waiting for connection...`, and use a 10-minute remote-assistance validity window. Windows must expose those entry points without starting WebRTC offerer/answerer, signaling WebSocket rooms, HTTP file services, or `FfiEngineClient` until the trust and adapter path is explicit.
- The cross-network `Generate QR Code` surface retains its existing signed envelope/preview boundary. File Transfer `Generate QR` is unavailable until an actual share manifest and service exist; the former empty, signed share-intent implementation was removed.
- Windows discovery should use a replaceable DNS-SD browser boundary. Microsoft currently marks WinRT `Windows.Networking.ServiceDiscovery.Dnssd.DnssdServiceWatcher` as unsupported and directs developers to Win32 `windns.h` APIs such as `DnsServiceBrowse` and `DnsServiceRegister`, so `WindowsDiscoveryBrowserClient` documents the live adapter boundary without binding the product to the unsupported watcher API.
- `WindowsDiscoveryBrowserClient` also owns `DiscoveryBrowserInputPolicy`, including the 15-second Extended Search default and the ordered `_skybridge._udp`, `_skybridge._tcp`, `_skybridge-xfer._tcp`, `_skybridge-rd._tcp`, `_skybridge-transfer._tcp`, `_skybridge-remote._tcp` query set. Canonical product services are queried before legacy aliases, and aliases are normalized before route projection. `SessionViewModel` can display and submit those values without hardcoding discovery policy. Its native provider boundary is `IWindowsDnsSdBrowseClient`: the default `PendingWindowsDnsSdBrowseClient` returns a visible pending fact, while `NativeWindowsDnsSdBrowseClient` wraps Win32 `DnsServiceBrowse`, `DnsServiceResolve`, cancel, and free callbacks to produce `WindowsDnsSdResolvedTxtRecord` values that are still parsed through `CoreDiscoveryClient`. Native TXT properties first pass through `NativeWindowsDnsSdTxtRecordCodec`, which rejects duplicate keys, separator/control injection, and property/byte-limit violations instead of truncating or trusting raw TXT text. The live provider is intentionally not the default dependency until local-network acceptance proves real mac/iOS advertisements resolve safely.
- DNS-SD browser lifecycle is exact-owner: every browser operation receives a monotonic generation plus an opaque lease, replacement cancels only the superseded lease, and Stop captures only the active lease visible at its invocation. Win32 browse cancellation awaits the documented final `ERROR_CANCELLED` callback, resolve awaits its completion callback, and managed query context/delegate memory remains owned until that callback barrier completes; a fixed callback-drain delay is forbidden. `DiscoveryBrowserActions` publishes a post-`await` snapshot only through `WindowsDiscoveryBrowserClient.TryPublish`, so stale Start/Stop A cannot overwrite replacement B.
- `WindowsDiscoveryBrowserClient` returns `DiscoveryBrowserPeerCandidate` values for discovered-peer rows, keeping `CapabilitiesSummary` and the fingerprint-only trust summary beside the browser boundary while preserving the original `DiscoveredPeer` for pairing and preflight.
- `WindowsDiscoveryBrowserClient` owns Discovery Browser pending status text for Start/Stop/Refresh/ExtendedSearch actions, so `SessionViewModel` no longer branches on discovery actions to produce `Scanning...` / `Stopping...`.
- The Rust core now exposes `transport` selection primitives, transport binding transcript digests, plus `skybridge_select_transport` and `skybridge_transport_binding_digest` over FFI so the Windows UI and adapters can request auditable transport facts instead of hardcoding protocol state.
- Windows connection preflight now uses the replaceable `IWindowsTransportAdapterClient` boundary between Core transport planning and launch. The default `PendingWindowsTransportAdapterClient` supplies explicit preflight endpoint/candidate/exporter placeholder material and keeps `IsLiveAdapterReady` false; it rejects `AppleNative` at the Windows adapter boundary, and future WebRTC, MsQuic, relay, or TCP adapters must replace that snapshot with live local/remote endpoints, selected candidate pair, exporter fingerprint, relay id, timestamp window, and capability digest before Connect can leave the preflight-only path. `VerifiedWebRtcDataChannelTransportAdapterClient` is the first WebRTC-specific live boundary: it accepts only a fresh helper proof that matches the pairing peer/fingerprint, confirms WebRTC DataChannel open, confirms an `SBF1` echo frame, and carries endpoint/candidate/digest material before returning `IsLiveAdapterReady=true`. `ConnectionWorkspaceStateClient.BuildConnectionLaunchReadiness` remains the request-shape gate used by `BuildConnectionLaunchRequest`, while `BuildLiveConnectionLaunchReadiness` is the UI/session command gate that also requires a live Windows adapter so preflight-only requests fail closed in execution but do not leave Connect enabled.
- `ConnectionPreflightPlan` carries the full Core launch contract, including selected transport/audit, suite/wire ID/audit, SBP2/frame metadata, transport binding digest, adapter endpoints/candidate/relay/timestamp, and all five typed Core channel mappings. Windows launch validation and Rust `SessionTransportBinding.validate()` both reject channel binding kinds that do not match the selected transport, so Windows WebRTC/MsQuic/relay/TCP paths cannot accidentally consume Apple stream/datagram bindings. `FfiEngineClient` marshals that contract into `SkybridgeSessionConfig`; Rust parses it into `SessionTransportBinding`, rejects incomplete or mismatched fields, stores it on `SessionConfig`, and exposes the selected transport plus digest through `skybridge_engine_snapshot` for interop smoke checks.
- `WindowsNativeRuntimeDependencyFactory` is the product composition root for the real Windows lifecycle. Default configured startup now uses `FfiEngineClient` for the session engine and `PendingWindowsTransportAdapterClient` for the transport boundary, so Core lifecycle state is real while connection launch still fails closed until a live adapter supplies endpoint/candidate/exporter/relay/timestamp/capability binding material. `SkybridgeNativeLibraryResolver` registers the `skybridge_core` P/Invoke resolver for `FfiEngineClient` and `CoreBridge`; it loads only the platform native library from `AppContext.BaseDirectory` and reports a `DllNotFoundException` if the app output does not contain that artifact, rather than searching `PATH` or falling back to a simulated engine. `SKYBRIDGE_WINDOWS_RUNTIME=native` no longer decides whether the engine is real; it opts the discovery profile into `NativeWindowsDnsSdBrowseClient` for local-network acceptance. `SKYBRIDGE_WINDOWS_TRANSPORT_ADAPTER=external` requires `SKYBRIDGE_WINDOWS_ADAPTER_BINDING`, `SKYBRIDGE_WINDOWS_LOCAL_ENDPOINT`, `SKYBRIDGE_WINDOWS_REMOTE_ENDPOINT`, `SKYBRIDGE_WINDOWS_SELECTED_CANDIDATE_PAIR`, `SKYBRIDGE_WINDOWS_TRANSPORT_SECRET_FP_HEX`, and `SKYBRIDGE_WINDOWS_CAPABILITY_DIGEST_HEX` before `ExternalWindowsTransportAdapterClient` can return `IsLiveAdapterReady=true`. `SKYBRIDGE_WINDOWS_TRANSPORT_ADAPTER=webrtc-verified` requires `SKYBRIDGE_WINDOWS_WEBRTC_PROOF_PATH` and optional positive `SKYBRIDGE_WINDOWS_WEBRTC_PROOF_MAX_AGE_MS` so a real WebRTC helper can prove DataChannel/SBF1 liveness before binding material is accepted. `SKYBRIDGE_WINDOWS_RELAY_ID` is optional external binding material, `SKYBRIDGE_WINDOWS_ADAPTER_KIND` may pin the external adapter to the Core-selected kind, and `SKYBRIDGE_WINDOWS_TIMESTAMP_WINDOW_MS` defaults to 10000 but must stay positive when provided. `SKYBRIDGE_WINDOWS_SETTINGS_SYSTEM_PREFERENCES=enabled` is a separate Settings provider gate that selects `WindowsSystemPreferencesLauncher`; without it, `DisabledSystemPreferencesLauncher` keeps the `Open System Preferences` action fail-closed. Without the adapter gate, configured runtime uses `PendingWindowsTransportAdapterClient`. Pending, external, and verified WebRTC Windows adapters reject `AppleNative` before producing binding material, and `ConnectionPreflightPlan.ValidateForLaunch` rejects any Windows launch request whose Core transport or adapter kind is `AppleNative`, so Apple-to-Apple remains on the Apple native path and cannot be claimed by the Windows adapter boundary or a hand-built launch request.
- `CurrentPathSignalingClient` now mirrors the Mac current-path control-plane contract at the Windows service boundary: it validates protocol identity bindings with the same authoritative fingerprint transcript, canonicalizes signaling origins, rejects query-token websocket authentication, builds only header-authenticated websocket URLs/headers, parses admission/register-code/lookup responses fail-closed with redacted server rejection bodies, and owns a header-auth `CurrentPathWebSocketSignalingClient` whose lifecycle stays `connecting -> socketOpen -> bound` before any signaling envelope can be sent. The Windows WebRTC envelope codec uses the `sessionId/from/to/type/payload/sentAt` JSON fields, rejects unknown fields, unknown frame types, and any business-frame `authToken`; credentials stay in the WebSocket headers only. Server `bound` is treated as signaling readiness only. This is still not a production UI launch path: the Windows shell does not yet register/lookup a live code from user-visible controls, but RuntimeSmoke live gates can prove admission/register/lookup, header-bound signaling, and server-backed current-path SDP/ICE transport into the `mac-product-control-v1` helper path. Those gates must still keep `TransportOnly`, `HandshakeEstablished`, and `AppControlReady` as separate evidence states until the product runtime composes current-path signaling with WebRTC adapter binding, pairing identity material, responder/initiator handshake policy, and Mac/iOS product App live gates.
- `channel.rs` maps Core logical channels to adapter-specific channel names and exposes them through `ConnectionPlan.ChannelMappings` plus the low-level `skybridge_map_channel` / `CoreBridge.MapChannelAsync` diagnostic helper: MsQuic uses streams for control/file/clipboard and datagrams for telemetry/realtime; WebRTC uses separate DataChannel labels per logical channel; Apple native keeps the same Core names without switching Apple-to-Apple to WebRTC.
- The Rust core also defines the ADR canonical crypto suite IDs (`0x0001`, `0x0101`, `0x1001`, `0x1002`) in `suite.rs`; offered suites are derived from runtime provider capabilities and classic fallback requires an explicit policy gate.
- The Rust core provides SBP2 traffic-padding framing in `padding.rs` using the ADR wire shape (`SBP2` magic, `actual_len` u32be, payload, random padding). Transport adapters still need to call it after handshake policy enables padding.
- `frame.rs` defines the Core channel frame envelope (`SBF1` magic, version, channel, flags, sequence, payload length, payload) so MsQuic/WebRTC/Relay adapters can carry the same framed payloads. SBP2-padded payloads are flagged in the frame rather than inferred by transport-specific code, and `skybridge_encode_frame` / `skybridge_encode_sbp2_frame` / `skybridge_decode_frame_metadata` / `skybridge_decode_frame_payload` expose that codec to Windows through `CoreBridge.EncodeFrameAsync`, `CoreBridge.EncodeSbp2FrameAsync`, `CoreBridge.DecodeFrameMetadataAsync`, and `CoreBridge.DecodeFramePayloadAsync`.
- `connection.rs` combines transport selection, crypto suite negotiation, logical-channel binding, SBP2 policy, and frame metadata into one auditable Core connection plan. It is exposed through `skybridge_plan_connection` and `CoreBridge.PlanConnectionAsync` so Windows adapters and UI can consume this plan instead of re-deriving protocol decisions in C#.

## 2026-09-01 reconciliation: ADR-0001 §6.2 against the implementation

ADR-0001 is dated 2026-06-07. This section records what three months of implementation
confirmed, what diverged, and what the ADR does not yet cover. It changes no decision; it
states where the code stands against one, so the next piece of work starts from facts.

**What holds.** MsQuic is reached through `System.Net.Quic` (MsQuic v2.6.1), matching the
ADR's "MsQuic 2.5+" baseline, and dial/listen/secret-binding all consume
`SkyBridgeProtocolConstants.MsQuicAlpn` = `skybridge-sbq/1`. PQC runs the dual track the ADR
asked for: the .NET 10 platform APIs (`MLKem`/`MLDsa`) where available, with the Rust core's
`ml-kem 0.3.2` / `ml-dsa 0.1.1` / `x-wing 0.1.0` as the provider fallback. Core still owns
identity, pairing, trust, handshake, channels, selection, padding and audit.

**Divergence — the ADR's default path is not the product's default path.** §6.2 names
`WindowsNativeMsQuicTransport` as the Windows ↔ Windows default. In
`WindowsNativeRuntimeDependencyFactory.CreateTransportAdapterFromEnvironment`, the default
with no environment set is `PendingWindowsTransportAdapterClient`; MsQuic is selected only by
`SKYBRIDGE_WINDOWS_TRANSPORT_ADAPTER=msquic` plus `SKYBRIDGE_WINDOWS_MSQUIC_ROLE` and a
hand-supplied `..._PEER_ENDPOINT` / `..._LISTEN_ENDPOINT`. The adapter is real
(`WindowsNativeMsQuicTransportAdapterClient`, `WindowsNativeMsQuicListenerTransportAdapterClient`),
but it is reachable as a lab harness, not as a product path. Everything downstream fail-closes
accordingly in the generic engine path. The dedicated native file-transfer and remote-desktop
entries now use the shared device workspace described above; they do not turn the generic
preflight path into a live adapter.

**The missing link the ADR does not specify.** §6.2 gives a discovery row and a transport row
but no step that turns a discovered peer into the endpoint the adapter needs. Preflight ends
at a `ConnectionPreflightPlan` whose `LocalEndpoint` / `RemoteEndpoint` / `SelectedCandidatePair`
stay `adapter pending`, and `ConnectionLaunchRequest` refuses with "Connection launch requires
a live Windows transport adapter; the current request is preflight-only." The generic connection entry still requires complete runtime composition. The concrete LAN
file-transfer and remote-desktop entries now bind their discovered routes to their existing
authenticated device-session owner.

**That binding landed on 2026-09-01, and here is exactly how far it goes.** The routes
discovery already resolved travel to the adapter over the path that was already there, with no
parallel structure added: `DiscoveryBrowserPeerCandidate.Routes` is carried by
`ConnectionWorkspaceValidatedState.DiscoveryCandidate`, which every state transition already
preserves, so `ConnectionWorkspaceActions.PrepareConnectionAsync` can hand it to
`IConnectionPreflightClient.BuildReadOnlySnapshotAsync` as an optional argument; preflight puts
it on `WindowsTransportAdapterRequest.DiscoveredRoutes`, the one place that record is
constructed. `WindowsNativeMsQuicTransportAdapterClient.ResolveDialTarget` then prefers a
pinned `SKYBRIDGE_WINDOWS_MSQUIC_PEER_ENDPOINT`, falls back to the resolved control route, and
throws when it has neither — it never invents an address. The dial-role endpoint variable is
consequently read with `Optional` rather than `Required`; the listen role keeps `Required`,
because a local bind address is not something discovery can supply. The pure route records
moved to `Services/DiscoveryPeerRoutes.cs` as `partial` halves so preflight and the adapters can
carry them without depending on the DNS-SD browse machinery; the `FromResolvedTxtRecord`
factories stay with that machinery in `DiscoveryBrowserClient.cs`.

What this does **not** do is flip the default. `CreateTransportAdapterFromEnvironment` still
returns `PendingWindowsTransportAdapterClient` with no environment set, so File Transfer and
Remote Desktop still fail closed exactly as described above. Flipping it is a separate decision
that needs two Windows hosts to verify end to end, and it should not be made on the strength of
a gate that never opens a socket.

**A discovery tier the ADR is missing.** §6.2's discovery row is "Windows DNS-SD / mDNS" only.
mDNS cannot cross a subnet, and real deployments separate peers by VLAN: measured on
2026-08-31, one building put wired clients on `10.101.104.0/23` and wireless on
`192.168.110.0/24`, so LAN discovery between them is impossible by construction rather than by
defect. An account-scoped tier already exists server-side and predates this note —
`public.registered_devices(user_id, device_id, device_name, status, last_seen_at)` in
`Server/skybridge-signaling/sql/security_v5.sql`, readable with the anon key plus a user access
token per `lib/registry_store.js`, with `/api/devices/register-current` and the enrollment
routes for the write side — but no client read it until
`Services/AccountDeviceRosterClient.cs` (2026-08-31). §6.2's discovery row should read as a
tier: mDNS for same-subnet, account registry for everything else, signaling/relay for NAT.

**A constraint to re-check rather than design around.** `channel.rs` maps the telemetry and
realtime channels to `MsQuicDatagram`, but `System.Net.Quic` does not expose the QUIC datagram
extension (RFC 9221), so those channels currently have no unreliable transport on Windows —
recorded in `WindowsNativeMsQuicTransportAdapterClient`. Re-check whether a later .NET exposes
it before considering a direct msquic.dll interop path, since that would add a second transport

- Keep the Mac product-control transport shell as a separate `mac-product-control-v1` profile. The helper modes `product-control-offer` / `product-control-answer` must create or accept only the `skybridge` DataChannel label and expose a loopback IPC whose messages are 4-byte big-endian length-prefixed raw control chunks capped at 8192 bytes. `WebRtcProductControlTransportProvider` owns the WinClient service boundary for launching that helper profile, parsing the shared SDP signaling via `WebRtcSignalDocument`, binding the run to pairing identity/fingerprint, and returning a `LiveWebRtcProductControlContext`; `WebRtcProductControlPlaneClient` consumes the raw IPC. The codec is intentionally cryptography-free; it must feed the service-layer `WebRtcProductHandshakeDriver` rather than marking sessions established by itself. `WebRtcProductHandshakeDriver` owns both product-control handshake roles over the raw control plane: the initiator sends MessageA, verifies MessageB and responder FINISHED, sends initiator FINISHED, and installs a session; the responder reads MessageA, verifies the initiator identity/fingerprint/policy before decapsulation, sends MessageB and responder FINISHED, verifies initiator FINISHED, and then installs a responder session. It must depend on `IWebRtcProductHandshakeCryptoProvider` for identity signing and key agreement; `UnavailableWebRtcProductHandshakeCryptoProvider` is a fail-closed placeholder, not a product fallback. `WebRtcProductPqcHandshakeCryptoProvider` supports the initiator role only when explicit peer ML-KEM-768 public key material is injected, and supports the responder role only when local ML-KEM-768 decapsulation key material is injected; responder live gates must also provide matching local ML-KEM public key material so the key-pair provenance can be hashed and verified without logging key bytes. Missing material fails the requested role instead of falling back to another suite. `WebRtcProductHandshakeSessionKeys` owns the Mac-compatible KDF/session-id/FINISHED boundary once that verified driver supplies a real 32-byte shared secret, transcriptA/B hashes, suite wire id, and client/server nonces; it also stays provider-agnostic and must not be called with legacy Rust `SessionSecrets` or fixed test material in production. `WebRtcProductSecureSessionStore` is the only WinClient service allowed to install those derived session keys into an `Established` product-control context, and it must reject peer, fingerprint, adapter-binding, or transport-binding mismatches before exposing keys. `WebRtcProductControlSmokeClient` may write `TransportOnly` evidence for helper-to-helper raw chunk liveness, but that evidence must explicitly state that it is not Mac product app, product signaling, handshake, or secure session-key proof; the WinClient `webrtc-product-control` product composition rejects `SKYBRIDGE_WINDOWS_WEBRTC_PRODUCT_SMOKE` so raw smoke cannot become a product success path. `WebRtcControlChannelCodec` owns both the Windows SBWC envelope contract (magic/version/header length, packet type, direction, session hash, transcript prefix, epoch, counter, AES-GCM tag, and replay window) and the explicit legacy AppControl AES-GCM `SealedBox.combined` compatibility wire format. `WebRtcAppControlBootstrapClient` and `WebRtcAppControlResponderHost` must select that payload format explicitly. The current live AppControl proof uses `SkybridgeSecureEnvelopeV1`; a legacy compatibility proof, when explicitly selected, authenticates and encrypts one `nonce|ciphertext|tag` business frame but has no SBWC envelope, counter, AAD, or replay-window proof, and evidence must record that boundary explicitly. Passing the local driver/runtime smoke proves Windows can progress from `HandshakeEstablished` to an authenticated `AppControlReady` exchange against a test peer, but it is not persisted peer-trust proof or product UI-composition proof unless the evidence says so explicitly.
- Product-control lifecycle cleanup is owner-bound at two levels. Every `IWebRtcProductControlRuntimeConsumer.StartAsync` returns an opaque runtime lease that its matching Stop must present, while every installed secure session receives a separate `WebRtcProductSessionIncarnation` carried by the Established context. `WebRtcProductControlEngineClient` serializes Connect, Disconnect, Heartbeat, and Dispose; it stages returned leases under one connect-operation owner, publishes them atomically only after all consumers start, and stops that exact operation before disconnecting the inner engine or disposing its transport. The only ownerless store reset is explicitly named `ClearAllForGlobalShutdown` and is restricted to the runtime consumer's global Dispose boundary; ordinary Stop and startup-failure cleanup clear their exact Established context.
