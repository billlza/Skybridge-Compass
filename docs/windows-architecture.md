# Skybridge Windows client architecture

The WinUI client is organized to keep UI binding, engine integration, and platform FFI clearly separated so the Rust core can be slotted in without disrupting the shell.

## ADR alignment
- The current TDSC mac branch checked on 2026-06-07 is `origin/tdsc-2026-01-0318-ios-sim-fix` at `23ba063` (`Harden current-path release and discovery flows`). In the fetched remote state, that branch does not contain `Docs/ADR-0001-SkyBridge-Core-Transport-Matrix.md`; it contains the current-path architecture notes `Docs/CoreLayering.md`, `Docs/ProtocolAlignmentPlan.md`, and `Docs/CrossPlatformDiscoveryDesign.md`.
- `Docs/CoreLayering.md` on the current TDSC branch is the authority for the latest Apple modularization boundary: `SkyBridgeProtocolCore` owns protocol contracts and wire/control-plane models without AppKit, CloudKit, or Network.framework; `SkyBridgeAppleTransport` owns Apple-only transport implementation; `SkyBridgeCore` keeps existing runtime/UI integrations through compatibility aliases. Windows must mirror that separation instead of importing Apple transport assumptions into the Windows shell.
- `Docs/ProtocolAlignmentPlan.md` on the current TDSC branch is the authority for handshake reality: the binary handshake path is the only wire protocol, legacy JSON handshake is no longer present, and remaining legacy compatibility is limited to strict identity-key decoding. Windows connection planning must preserve that default and must not introduce a second JSON handshake path.
- The transport-matrix ADR remains available as `Docs/ADR-0001-SkyBridge-Core-Transport-Matrix.md` on `origin/tdsc-2026-01-0318-ios-sim-fix-20260211-adr` at `265f95d` (ADR Version 1.0, 2026-06-07). It treats WebRTC, MsQuic, and Apple Network.framework as transport adapters. SkyBridge Core owns identity, pairing, trust, handshake, logical channels, transport selection, traffic padding, and audit semantics. It also marks paper materials as stale for architecture decisions, so this Windows plan uses the current TDSC code/docs plus the ADR/code/README boundary rather than stale paper claims.
- `Docs/CrossPlatformDiscoveryDesign.md` on the current TDSC branch is a 2026-01-11 draft and is lower precedence than the ADR, current code, and Microsoft API guidance. Its Windows Bonjour SDK recommendation is retained only as historical context; the Windows implementation plan follows the replaceable Win32 DNS-SD boundary below.
- Windows-to-Windows same-LAN sessions must prefer `WindowsNativeMsQuicTransport`; Windows-to-Apple MVP interop should use `WebRTCInteropTransport`; Apple-to-Apple remains Apple native and must not be replaced by WebRTC by default.
- Apple discovery advertises `_skybridge._udp` as QUIC primary and `_skybridge._tcp` as fallback, with TXT fields `deviceId`, `pubKeyFP`, `platform`, `capabilities`, `name`, and `version`. `discovery.rs` parses and validates that shape so Windows discovery can consume mac/iOS advertisements without changing Apple Bonjour semantics, and `skybridge_parse_discovery_advertisement` / `CoreBridge.ParseDiscoveryAdvertisementAsync` expose the same parser to Windows DNS-SD or pairing services.
- The TDSC mac top-bar manual connection surface keeps IP Address blank by default, Port at `11550`, and Pairing Code blank. Its manual path constructs an `_skybridge._tcp` target only after user input, so Windows must mirror those fields without treating a typed code as a trusted peer key or bypassing discovery/pairing/trust checks.
- Windows production defaults keep Bonjour TXT and pairing-code inputs blank; sample mac advertisements and `skybridge-pair:v1` material belong in tests or explicit developer fixtures, not startup UI state.
- The TDSC mac cross-network connection surface includes `Dynamic Encrypted QR Code` and `Smart Connection Code`: QR uses `skybridge://connect/<base64url-json>` and scan accepts `skybridge://connect?data=<base64url-json>`. The current mac QR payloads include `DynamicQRCodeData` (`version`, `sessionID`, `deviceName`, `deviceFingerprint`, `publicKey`, `signingPublicKey`, `signature`, `signatureTimestamp`, `iceServers`, `expiresAt`), the older `SignedQRPayload` wrapper, and QR signature-test query/envelope forms using `sig`, `pk`, `ts`, `fp`, `signatureBase64`, `publicKeyBase64`, `timestamp`, and `publicKeyFingerprint`. TDSC signs dynamic QR with the `P2PSecurityManager` canonical string `id|name|type|address|port|os|cap|ts|fp`, but the current `DynamicQRCodeData` does not carry the signed `osVersion`, so Windows must treat current dynamic QR bodies as `unverifiable` after schema/key/timestamp/expiry validation. Windows verifies legacy/canonical P256 signatures where the payload contains the full canonical material, and verifies dynamic QR only when a future or supplemental payload supplies the signed OS version needed to rebuild that canonical string. Smart codes are 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, show `Waiting for connection...`, and use a 10-minute remote-assistance validity window. Windows must expose those entry points without starting WebRTC offerer/answerer, signaling WebSocket rooms, HTTP file services, or `FfiEngineClient` until the trust and adapter path is explicit.
- Windows discovery should use a replaceable DNS-SD browser boundary. Microsoft currently marks WinRT `Windows.Networking.ServiceDiscovery.Dnssd.DnssdServiceWatcher` as unsupported and directs developers to Win32 `windns.h` APIs such as `DnsServiceBrowse` and `DnsServiceRegister`, so `WindowsDiscoveryBrowserClient` documents the live adapter boundary without binding the product to the unsupported watcher API.
- `WindowsDiscoveryBrowserClient` also owns `DiscoveryBrowserInputPolicy`, including the 15-second Extended Search default and `_skybridge._udp` / `_skybridge._tcp` query order, so `SessionViewModel` can display and submit those values without hardcoding discovery policy. Its native provider boundary is `IWindowsDnsSdBrowseClient`: the default `PendingWindowsDnsSdBrowseClient` returns a visible pending fact, while `NativeWindowsDnsSdBrowseClient` wraps Win32 `DnsServiceBrowse`, `DnsServiceResolve`, cancel, and free callbacks to produce `WindowsDnsSdResolvedTxtRecord` values that are still parsed through `CoreDiscoveryClient`. The live provider is intentionally not the default dependency until local-network acceptance proves real mac/iOS advertisements resolve safely.
- `WindowsDiscoveryBrowserClient` returns `DiscoveryBrowserPeerCandidate` values for discovered-peer rows, keeping `CapabilitiesSummary` and the fingerprint-only trust summary beside the browser boundary while preserving the original `DiscoveredPeer` for pairing and preflight.
- `WindowsDiscoveryBrowserClient` owns Discovery Browser pending status text for Start/Stop/Refresh/ExtendedSearch actions, so `SessionViewModel` no longer branches on discovery actions to produce `Scanning...` / `Stopping...`.
- The Rust core now exposes `transport` selection primitives, transport binding transcript digests, plus `skybridge_select_transport` and `skybridge_transport_binding_digest` over FFI so the Windows UI and adapters can request auditable transport facts instead of hardcoding protocol state.
- Windows connection preflight now uses the replaceable `IWindowsTransportAdapterClient` boundary between Core transport planning and launch. The default `PendingWindowsTransportAdapterClient` supplies explicit preflight endpoint/candidate/exporter placeholder material and keeps `IsLiveAdapterReady` false; future WebRTC, MsQuic, relay, or TCP adapters must replace that snapshot with live local/remote endpoints, selected candidate pair, exporter fingerprint, relay id, timestamp window, and capability digest before Connect can leave the preflight-only path. `ConnectionWorkspaceStateClient.BuildConnectionLaunchReadiness` remains the request-shape gate used by `BuildConnectionLaunchRequest`, while `BuildLiveConnectionLaunchReadiness` is the UI/session command gate that also requires a live Windows adapter so preflight-only requests fail closed in execution but do not leave Connect enabled.
- `ConnectionPreflightPlan` carries the full Core launch contract, including selected transport/audit, suite/wire ID/audit, SBP2/frame metadata, transport binding digest, adapter endpoints/candidate/relay/timestamp, and all five typed Core channel mappings. `FfiEngineClient` marshals that contract into `SkybridgeSessionConfig`; Rust parses it into `SessionTransportBinding`, rejects incomplete or mismatched fields, stores it on `SessionConfig`, and exposes the selected transport plus digest through `skybridge_engine_snapshot` for interop smoke checks.
- `WindowsNativeRuntimeDependencyFactory` keeps the live Windows runtime behind explicit environment gates. `SKYBRIDGE_WINDOWS_RUNTIME=native` selects `FfiEngineClient` plus `NativeWindowsDnsSdBrowseClient`; `SKYBRIDGE_WINDOWS_TRANSPORT_ADAPTER=external` additionally requires `SKYBRIDGE_WINDOWS_ADAPTER_BINDING`, `SKYBRIDGE_WINDOWS_LOCAL_ENDPOINT`, `SKYBRIDGE_WINDOWS_REMOTE_ENDPOINT`, `SKYBRIDGE_WINDOWS_SELECTED_CANDIDATE_PAIR`, `SKYBRIDGE_WINDOWS_TRANSPORT_SECRET_FP_HEX`, and `SKYBRIDGE_WINDOWS_CAPABILITY_DIGEST_HEX` before `ExternalWindowsTransportAdapterClient` can return `IsLiveAdapterReady=true`. `SKYBRIDGE_WINDOWS_RELAY_ID` is optional binding material, `SKYBRIDGE_WINDOWS_ADAPTER_KIND` may pin the external adapter to the Core-selected kind, and `SKYBRIDGE_WINDOWS_TIMESTAMP_WINDOW_MS` defaults to 10000 but must stay positive when provided. Without that adapter gate, native runtime still uses `PendingWindowsTransportAdapterClient`. The external Windows adapter rejects `AppleNative` whether it is configured explicitly or passed in from Core selection, and `ConnectionPreflightPlan.ValidateForLaunch` rejects any Windows launch request whose Core transport or adapter kind is `AppleNative`, so Apple-to-Apple remains on the Apple native path and cannot be claimed by the Windows external binding or a hand-built launch request.
- `channel.rs` maps Core logical channels to adapter-specific channel names and exposes them through `ConnectionPlan.ChannelMappings` plus the low-level `skybridge_map_channel` / `CoreBridge.MapChannelAsync` diagnostic helper: MsQuic uses streams for control/file/clipboard and datagrams for telemetry/realtime; WebRTC uses separate DataChannel labels per logical channel; Apple native keeps the same Core names without switching Apple-to-Apple to WebRTC.
- The Rust core also defines the ADR canonical crypto suite IDs (`0x0001`, `0x0101`, `0x1001`, `0x1002`) in `suite.rs`; offered suites are derived from runtime provider capabilities and classic fallback requires an explicit policy gate.
- The Rust core provides SBP2 traffic-padding framing in `padding.rs` using the ADR wire shape (`SBP2` magic, `actual_len` u32be, payload, random padding). Transport adapters still need to call it after handshake policy enables padding.
- `frame.rs` defines the Core channel frame envelope (`SBF1` magic, version, channel, flags, sequence, payload length, payload) so MsQuic/WebRTC/Relay adapters can carry the same framed payloads. SBP2-padded payloads are flagged in the frame rather than inferred by transport-specific code, and `skybridge_encode_frame` / `skybridge_encode_sbp2_frame` / `skybridge_decode_frame_metadata` / `skybridge_decode_frame_payload` expose that codec to Windows through `CoreBridge.EncodeFrameAsync`, `CoreBridge.EncodeSbp2FrameAsync`, `CoreBridge.DecodeFrameMetadataAsync`, and `CoreBridge.DecodeFramePayloadAsync`.
- `connection.rs` combines transport selection, crypto suite negotiation, logical-channel binding, SBP2 policy, and frame metadata into one auditable Core connection plan. It is exposed through `skybridge_plan_connection` and `CoreBridge.PlanConnectionAsync` so Windows adapters and UI can consume this plan instead of re-deriving protocol decisions in C#.

## Technology stack check
- **WinUI shell:** `net10.0-windows10.0.19041.0` with Windows App SDK `2.1.3` and Windows SDK BuildTools `10.0.28000.1839`. Microsoft .NET 10 release metadata and support policy checked on 2026-06-09 list .NET 10 as active LTS, latest runtime `10.0.8`, and end of support on November 14, 2028. NuGet checked on 2026-06-09 lists `Microsoft.WindowsAppSDK` `2.1.3` as the current stable package while `2.1.4-experimental8` remains non-stable, and lists `Microsoft.Windows.SDK.BuildTools` `10.0.28000.1839` as the current stable package.
- **Windows native transport:** MsQuic remains the intended native QUIC adapter for Windows-to-Windows paths. GitHub release evidence checked on 2026-06-09 shows MsQuic v2.5.8 as the latest stable release while v2.5.9-rc remains prerelease; it should sit below SkyBridge Core transport binding and emit ETW/EventSource-style diagnostics rather than owning session identity.
- **WebRTC interop:** Use a native DataChannel adapter such as libdatachannel for Windows-to-Apple MVP interop. libdatachannel remains active in 2026, with GitHub releases checked on 2026-06-09 showing v0.24.4 as latest, and supports Windows plus Apple platforms, making it suitable as an adapter candidate, not as the protocol authority.
- **Rust core and CLI:** Keep the current Rust 2021 edition until a dedicated migration is scheduled. `src/cli.rs` and the `skybridge` binary are thin adapters over reusable Core functions; CLI smoke tests cover version, transport selection, transport binding digest including relay IDs, channel profile/map, frame describe, connection plan, discovery TXT parse, crypto suite offer/select, invalid-command behavior, and parser failure paths. `Scripts/verify-rust-cli-coverage.ps1` runs `cargo test` plus `cargo llvm-cov` and requires both total line coverage and `cli.rs` line coverage to stay at or above 90%. SBP2 padding has Core unit tests for fixed, bucketed, and malformed frame behavior.
- **Rust native FFI artifact:** `core/skybridge-core` builds both `rlib` and `cdylib` so the same Core code remains reusable by Rust tests/CLI and also produces the platform native library consumed by Windows `DllImport("skybridge_core")`. `Scripts/verify-rust-cli-coverage.ps1` now runs `cargo build --lib` and verifies the platform artifact (`skybridge_core.dll` on Windows, `libskybridge_core.dylib` on macOS, or `libskybridge_core.so` on Linux) before running tests and coverage.

- Consume typed `ConnectionPlan.ChannelMappings` from `CoreBridge.PlanConnectionAsync` as the workspace and preflight authority for Core logical-channel mappings. Keep `CoreBridge.MapChannelAsync` / `skybridge_map_channel` as a low-level single-channel diagnostic helper so Windows code does not duplicate adapter policy in C#.
- Use `CoreBridge.PlanConnectionAsync` / `skybridge_plan_connection` for the pre-adapter contract that combines selected transport, selected crypto suite, offered suites, channel bindings, frame header size, and SBP2 policy.
- Use `CoreBridge.EncodeFrameAsync`, `CoreBridge.EncodeSbp2FrameAsync`, `CoreBridge.DecodeFrameMetadataAsync`, and `CoreBridge.DecodeFramePayloadAsync` so Windows WebRTC/MsQuic/relay adapters carry Core-owned `SBF1` frames and unwrap SBP2 through Rust instead of duplicating framing logic in C#.
- Use `CoreBridge.ParseDiscoveryAdvertisementAsync` / `skybridge_parse_discovery_advertisement` so Windows discovery consumes mac/iOS Bonjour TXT advertisements through the same Core validation path as the CLI.
- Use `skybridge transport select` for operator smoke checks against the same Rust selector before WinUI or native adapter wiring is available.
- Use `skybridge transport bind` for operator smoke checks of the Core transport transcript digest before MsQuic/WebRTC/relay adapters are wired.
- Use `skybridge channel map` to verify that each transport adapter uses channel-specific streams, datagrams, or DataChannels before real adapter wiring is enabled.
- Use `skybridge frame describe` to verify Core channel frame metadata and SBP2 padding flags before real adapter wiring is enabled.
- Use `skybridge connection plan` to verify the full Core-owned pre-adapter contract: selected transport, selected crypto suite, offered suites, channel bindings, frame header size, and SBP2 policy.
- Use `skybridge discovery parse` to verify mac/iOS Bonjour TXT advertisements and service names before Windows DNS-SD wiring is enabled.
- Use `skybridge suite offer` and `skybridge suite select` to verify provider-derived suite offers, remote wire ID parsing, and downgrade audit behavior before platform crypto provider wiring is available.
- Map engine callbacks (state changes, input responses) to UI updates via events or observable properties on the view model.
- Keep heavy work off the UI thread by continuing to use async commands for connect/heartbeat; the FFI layer should marshal any blocking calls to thread-pool threads when necessary.
