# Skybridge Windows client architecture

The WinUI client is organized to keep UI binding, engine integration, and platform FFI clearly separated so the Rust core can be slotted in without disrupting the shell.

## ADR alignment
- The current TDSC mac branch checked on 2026-06-07 is `origin/tdsc-2026-01-0318-ios-sim-fix` at `23ba063` (`Harden current-path release and discovery flows`). In the fetched remote state, that branch does not contain `Docs/ADR-0001-SkyBridge-Core-Transport-Matrix.md`; it contains the current-path architecture notes `Docs/CoreLayering.md`, `Docs/ProtocolAlignmentPlan.md`, and `Docs/CrossPlatformDiscoveryDesign.md`.
- `Docs/CoreLayering.md` on the current TDSC branch is the authority for the latest Apple modularization boundary: `SkyBridgeProtocolCore` owns protocol contracts and wire/control-plane models without AppKit, CloudKit, or Network.framework; `SkyBridgeAppleTransport` owns Apple-only transport implementation; `SkyBridgeCore` keeps existing runtime/UI integrations through compatibility aliases. Windows must mirror that separation instead of importing Apple transport assumptions into the Windows shell.
- `Docs/ProtocolAlignmentPlan.md` on the current TDSC branch is the authority for handshake reality: the binary handshake path is the only wire protocol, legacy JSON handshake is no longer present, and remaining legacy compatibility is limited to strict identity-key decoding. Windows connection planning must preserve that default and must not introduce a second JSON handshake path.
- The transport-matrix ADR remains available as `Docs/ADR-0001-SkyBridge-Core-Transport-Matrix.md` on `origin/tdsc-2026-01-0318-ios-sim-fix-20260211-adr` at `265f95d` (ADR Version 1.0, 2026-06-07). It treats WebRTC, MsQuic, and Apple Network.framework as transport adapters. SkyBridge Core owns identity, pairing, trust, handshake, logical channels, transport selection, traffic padding, and audit semantics. It also marks paper materials as stale for architecture decisions, so this Windows plan uses the current TDSC code/docs plus the ADR/code/README boundary rather than stale paper claims.
- `Docs/CrossPlatformDiscoveryDesign.md` on the current TDSC branch is a 2026-01-11 draft and is lower precedence than the ADR, current code, and Microsoft API guidance. Its Windows Bonjour SDK recommendation is retained only as historical context; the Windows implementation plan follows the replaceable Win32 DNS-SD boundary below.
- Windows-to-Windows same-LAN sessions must prefer `WindowsNativeMsQuicTransport`; Windows-to-Apple MVP interop should use `WebRTCInteropTransport`; Apple-to-Apple remains Apple native and must not be replaced by WebRTC by default.
- Apple discovery advertises `_skybridge._udp` as QUIC primary and `_skybridge._tcp` as fallback, with TXT fields `deviceId`, `pubKeyFP`, `platform`, `capabilities`, `name`, and `version`. `discovery.rs` parses and validates that shape so Windows discovery can consume mac/iOS advertisements without changing Apple Bonjour semantics, and `skybridge_parse_discovery_advertisement` / `CoreBridge.ParseDiscoveryAdvertisementAsync` expose the same parser to Windows DNS-SD or pairing services.
- The TDSC mac top-bar manual connection surface keeps IP Address blank by default, Port at `11550`, and Pairing Code blank. Its manual path constructs an `_skybridge._tcp` target only after user input, so Windows must mirror those fields without treating a typed code as a trusted peer key or bypassing discovery/pairing/trust checks.
- The TDSC mac cross-network connection surface includes `Dynamic Encrypted QR Code` and `Smart Connection Code`: QR uses `skybridge://connect/<base64url-json>` and scan accepts `skybridge://connect?data=<base64url-json>`. The current mac QR payloads include `DynamicQRCodeData` (`version`, `sessionID`, `deviceName`, `deviceFingerprint`, `publicKey`, `signingPublicKey`, `signature`, `signatureTimestamp`, `iceServers`, `expiresAt`), the older `SignedQRPayload` wrapper, and QR signature-test query/envelope forms using `sig`, `pk`, `ts`, `fp`, `signatureBase64`, `publicKeyBase64`, `timestamp`, and `publicKeyFingerprint`. Windows validates those envelopes read-only, verifies legacy/canonical P256 signatures where the mac payload contains the full canonical material, enforces expiry and challenge windows, and marks `DynamicQRCodeData` as `pending canonical verifier` until the exact `P2PSecurityManager` canonical input is shared. Smart codes are 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, show `Waiting for connection...`, and use a 10-minute remote-assistance validity window. Windows must expose those entry points without starting WebRTC offerer/answerer, signaling WebSocket rooms, HTTP file services, or `FfiEngineClient` until the trust and adapter path is explicit.
- Windows discovery should use a replaceable DNS-SD browser boundary. Microsoft currently marks WinRT `Windows.Networking.ServiceDiscovery.Dnssd.DnssdServiceWatcher` as unsupported and directs developers to Win32 `windns.h` APIs such as `DnsServiceBrowse` and `DnsServiceRegister`, so `WindowsDiscoveryBrowserClient` documents the live adapter boundary without binding the product to the unsupported watcher API.
- The Rust core now exposes `transport` selection primitives, transport binding transcript digests, plus `skybridge_select_transport` and `skybridge_transport_binding_digest` over FFI so the Windows UI and adapters can request auditable transport facts instead of hardcoding protocol state.
- `channel.rs` maps Core logical channels to adapter-specific channel names and exposes them through `skybridge_map_channel` / `CoreBridge.MapChannelAsync`: MsQuic uses streams for control/file/clipboard and datagrams for telemetry/realtime; WebRTC uses separate DataChannel labels per logical channel; Apple native keeps the same Core names without switching Apple-to-Apple to WebRTC.
- The Rust core also defines the ADR canonical crypto suite IDs (`0x0001`, `0x0101`, `0x1001`, `0x1002`) in `suite.rs`; offered suites are derived from runtime provider capabilities and classic fallback requires an explicit policy gate.
- The Rust core provides SBP2 traffic-padding framing in `padding.rs` using the ADR wire shape (`SBP2` magic, `actual_len` u32be, payload, random padding). Transport adapters still need to call it after handshake policy enables padding.
- `frame.rs` defines the Core channel frame envelope (`SBF1` magic, version, channel, flags, sequence, payload length, payload) so MsQuic/WebRTC/Relay adapters can carry the same framed payloads. SBP2-padded payloads are flagged in the frame rather than inferred by transport-specific code, and `skybridge_encode_frame` / `skybridge_encode_sbp2_frame` / `skybridge_decode_frame_metadata` / `skybridge_decode_frame_payload` expose that codec to Windows through `CoreBridge.EncodeFrameAsync`, `CoreBridge.EncodeSbp2FrameAsync`, `CoreBridge.DecodeFrameMetadataAsync`, and `CoreBridge.DecodeFramePayloadAsync`.
- `connection.rs` combines transport selection, crypto suite negotiation, logical-channel binding, SBP2 policy, and frame metadata into one auditable Core connection plan. It is exposed through `skybridge_plan_connection` and `CoreBridge.PlanConnectionAsync` so Windows adapters and UI can consume this plan instead of re-deriving protocol decisions in C#.

## Technology stack check
- **WinUI shell:** `net10.0-windows10.0.19041.0` with Windows App SDK `2.1.3`. Microsoft lists .NET 10 as active LTS through November 2028, and the Microsoft Windows App SDK downloads page lists `2.1.3` as the current stable package/runtime checked on 2026-06-07.
- **Windows native transport:** MsQuic remains the intended native QUIC adapter for Windows-to-Windows paths. Microsoft/GitHub release evidence checked on 2026-06-07 shows MsQuic v2.5.8 as the current release line; it should sit below SkyBridge Core transport binding and emit ETW/EventSource-style diagnostics rather than owning session identity.
- **WebRTC interop:** Use a native DataChannel adapter such as libdatachannel for Windows-to-Apple MVP interop. libdatachannel remains active in 2026, with GitHub releases showing v0.24.3 as latest, and supports Windows plus Apple platforms, making it suitable as an adapter candidate, not as the protocol authority.
- **Rust core and CLI:** Keep the current Rust 2021 edition until a dedicated migration is scheduled. `src/cli.rs` and the `skybridge` binary are thin adapters over reusable Core functions; CLI smoke tests cover version, transport selection, transport binding digest including relay IDs, channel profile/map, frame describe, connection plan, discovery TXT parse, crypto suite offer/select, invalid-command behavior, and parser failure paths. `Scripts/verify-rust-cli-coverage.ps1` runs `cargo test` plus `cargo llvm-cov` and requires both total line coverage and `cli.rs` line coverage to stay at or above 90%. SBP2 padding has Core unit tests for fixed, bucketed, and malformed frame behavior.

## Layers
- **ViewModels** (`windows/Skybridge.WinClient/ViewModels`): presentation logic and bindable state. `SessionViewModel` owns connection status, bitrate/framerate selections, async commands for connect/disconnect/heartbeat, the manual Device Discovery TXT parser state, the USB Management stats/device snapshot state, the File Transfer queue/history/security snapshot state, the Remote Desktop session/control snapshot state, the Quantum/Core diagnostics snapshot state, the System Monitor overview/detail/indicator snapshot state, the Settings tabs/actions/details snapshot state, and busy-state handling to keep the UI responsive.
- **UI parity contract** (`docs/windows-ui-parity-contract.md`): fixes the Windows side navigation, top bar, dashboard metrics, and current shell contract against the macOS `NavigationItem` order. `FeatureEntryContract` mirrors the macOS entry order so missing Windows feature pages stay visible and testable.
- **Services** (`windows/Skybridge.WinClient/Services`): engine abstractions behind `IEngineClient`. The stub `DummyEngineClient` simulates connect/disconnect/heartbeat flows and remains the default shell dependency until native DLL deployment is explicit. `FfiEngineClient` implements the same interface over the Rust C ABI (`skybridge_engine_new`, local public key, connect, heartbeat, disconnect, state) so the UI can switch without moving connection logic into view models. It requires an `IPeerPublicKeyProvider` supplied by pairing/discovery and must not use the local public key as a fake peer key. `CoreDiscoveryClient` wraps `CoreBridge.ParseDiscoveryAdvertisementAsync` behind `IDiscoveryClient` and returns a `DiscoveredPeer` from Core-validated Bonjour TXT data; it preserves `pubKeyFP` as a fingerprint only and does not turn discovery data into a peer public key. `WindowsDiscoveryBrowserClient` wraps the Windows DNS-SD browse boundary behind `IDiscoveryBrowserClient`, exposes Start/Stop/Refresh/ExtendedSearch/Compatibility/Search state, preserves `_skybridge._udp` before `_skybridge._tcp`, and feeds any resolved TXT record through `CoreDiscoveryClient`; until live `DnsServiceBrowse` resolution is wired, it remains a read-only snapshot and does not synthesize peers. `ManualConnectionClient` validates the mac-parity Manual Host/IP, Port, and Code inputs behind `IManualConnectionClient`, normalizes a user-supplied host, enforces port `1..65535` with default `11550`, emits `_skybridge._tcp` target facts, and states that no connection is started; a code is routing or pairing input only, never a peer public key.
  `CrossNetworkConnectionClient` validates the mac-parity `Dynamic Encrypted QR Code` and `Smart Connection Code` envelopes behind `ICrossNetworkConnectionClient`, preserves `skybridge://connect/` plus `skybridge://connect?data=` QR formats, recognizes `SignedQRPayload`, `DynamicQRCodeData`, `QRCodeSignatureEnvelope`, and `QRCodeSignatureQuery`, enforces `version == 2`, `deviceFingerprint`, Curve25519 public-key length, P256 signing-key shape, raw signature length, expiry, and the 300-second signature challenge window, verifies legacy/canonical P256 signatures when the mac payload includes the full canonical material, marks dynamic QR signatures as `pending canonical verifier`, enforces the 6-character `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` short-code alphabet, reports `CrossNetworkReadiness` as `idle`, and states that no WebRTC offerer/answerer, signaling room, HTTP file server, or `FfiEngineClient` connection is started. `PairingMaterialClient` validates manual `skybridge-pair:v1` connection codes by decoding the peer public key, hashing it, and comparing the result to `pubKeyFP` plus any discovered fingerprint before producing an `IPeerPublicKeyProvider`; discovery fingerprints remain verification inputs only. `ConnectionPreflightClient` requires both a Core-validated `DiscoveredPeer` and pairing-derived `PairingMaterial`, then calls `CoreBridge.PlanConnectionAsync`, `CoreBridge.ComputeTransportBindingDigestAsync`, and `CoreBridge.MapChannelAsync` to render a read-only connection readiness snapshot; it does not call `FfiEngineClient.ConnectAsync`, does not switch the default engine, and labels its binding digest material as preflight-only until live adapters provide real endpoints, candidates, and DTLS/QUIC exporter fingerprints. `UsbManagementWorkspaceClient` wraps .NET `DriveInfo` removable-drive scanning behind `IUsbManagementWorkspaceClient` so USB Management can render stats and device detail fields without connecting/disconnecting devices, claiming MFi/Android identity, or inventing vendor/product/serial values. `FileTransferWorkspaceClient` wraps `CoreBridge.MapChannelAsync` and frame codec calls behind `IFileTransferWorkspaceClient` so the File Transfer page can render Core-owned queue/history/security facts without reading local files or starting transfers. `RemoteDesktopWorkspaceClient` wraps `CoreBridge.PlanConnectionAsync`, realtime/telemetry/control channel mapping, and SBP2 frame metadata behind `IRemoteDesktopWorkspaceClient` so the Remote Desktop page can render session, quality, and performance planning facts without starting capture, input forwarding, or a live display stream. `SystemMonitorWorkspaceClient` wraps .NET runtime, process, disk, and network-interface read-only APIs behind `ISystemMonitorWorkspaceClient` so System Monitor can render overview/details/indicators without installing helpers, elevating, or claiming unsupported temperature/GPU data. `SettingsWorkspaceClient` exposes read-only Settings tabs/actions/details behind `ISettingsWorkspaceClient` so the Settings page can render the macOS preference shape without importing/exporting files, requesting permissions, resetting preferences, applying settings, or mutating Core policy. `CoreDiagnosticsClient` wraps `CoreBridge.PlanConnectionAsync`, `CoreBridge.ComputeTransportBindingDigestAsync`, channel mapping, and frame codec calls behind `ICoreDiagnosticsClient` so Quantum diagnostics can render Core-owned protocol facts without duplicating policy in the view model.
- **Views** (`windows/Skybridge.WinClient/MainWindow.xaml`): XAML-only bindings with no business logic in code-behind. The window creates the view model and relies on commands/properties for interactions. The top bar mirrors the current TDSC mac order for connection state, FPS/diagnostics, notifications, and theme controls, then keeps the Windows `Heartbeat` action after those status controls. Device Discovery currently exposes mac-parity scan controls in ordered form (`Compatibility Mode`, `Extended Search`, `Manual Connect`, `Start Scan`, `Stop Scan`, `Refresh`, and device search), a manual target row (`Manual Host / IP`, `Port` default `11550`, `Code`), cross-network QR/code controls (`Dynamic Encrypted QR Code`, `Generate QR Code`, `Scan QR Code`, `Smart Connection Code`, `Generate Code`, `Copy`, `Regenerate`, `Connect`, `Waiting for connection...`), a Core-validated manual service/TXT parser, result list, pairing-code validator, pairing facts, and a `Prepare Connection` preflight snapshot that surfaces pairing verification, Core connection plan, transport binding digest, selected suite, SBP2, channel mapping, and the no-connection-started boundary; it does not start a real Windows DNS-SD browse, WebRTC session, signaling room, HTTP file service, or connection attempt until the native adapter is wired. USB Management currently exposes refresh, last-scan status, MFi/Android/storage/total stats, empty state, and device detail fields from a read-only removable-drive snapshot; it does not install drivers, start MFi/ADB/MTP providers, or mutate USB devices. File Transfer currently exposes disabled quick actions plus a read-only Core-backed queue/history/security workspace; it does not open file pickers, read local files, generate live QR codes, or start transfers. Remote Desktop currently exposes disabled recommended/advanced connect, performance overlay, quality, settings, fullscreen, and disconnect actions plus a read-only Core-backed session/control workspace; it does not capture screens, forward input, start RDP/WebRTC video, or terminate live sessions. Quantum currently exposes a read-only Core diagnostics panel for Windows-to-Apple interop transport, transport binding digest, suite, SBP2, channel binding, and frame metadata; it does not initiate a session. System Monitor currently exposes a read-only overview/details/indicator workspace with disabled monitoring/helper controls; it does not install a helper, start ETW sampling, or query unsupported thermal/GPU providers. Settings currently exposes refresh, export/import/reset, permissions, tab list, file-transfer/video-transfer/remote-desktop/system-monitor details, apply/default/reset-monitor actions, and Core/PQC policy status as a read-only workspace; all preference writes remain disabled, and future runtime application must stay separate from saving settings.

## Planned Rust FFI integration
- Wire `FfiEngineClient` into the app startup once the native `skybridge_core` DLL deployment path and pairing-derived `IPeerPublicKeyProvider` are defined; until then, keeping `DummyEngineClient` as the default prevents a missing DLL from breaking the text-only shell.
- Keep the Device Discovery browser wired through `WindowsDiscoveryBrowserClient(discoveryClient)`, the manual target validator wired through `ManualConnectionClient`, the cross-network QR/code validator wired through `CrossNetworkConnectionClient`, the parser wired through `CoreDiscoveryClient(coreBridge)`, the pairing-code validator wired through `PairingMaterialClient`, and the read-only connection preflight wired through `ConnectionPreflightClient(coreBridge)` for explicit validation while the real DNS-SD resolver, trust store, signaling, WebRTC/MsQuic adapter launch path, and native DLL deployment are pending. Missing native DLLs should surface as command errors instead of silently falling back to a fake parser or fake connection plan.
- Keep the USB Management workspace wired through `UsbManagementWorkspaceClient` for explicit removable-storage snapshots while MFi, Android ADB/MTP, USB descriptor/PnP metadata, safe eject, connect/disconnect notifications, and driver/provider integration are pending. Provider-pending fields should remain visible so mac parity gaps remain obvious.
- Keep the File Transfer workspace wired through `FileTransferWorkspaceClient(coreBridge)` for explicit queue/history/security snapshots while real file selection, QR share links, malware scanning, HMAC, signature verification, and transfer transport are pending. Disabled quick-action buttons should stay visible so mac parity gaps remain obvious.
- Keep the Remote Desktop workspace wired through `RemoteDesktopWorkspaceClient(coreBridge)` for explicit session/control snapshots while real recommended/advanced connect, display capture, input forwarding, performance overlay metrics, quality application, fullscreen, and disconnect behavior are pending. Disabled action buttons should stay visible so mac parity gaps remain obvious.
- Keep Quantum/Core diagnostics wired through `CoreDiagnosticsClient` for explicit, read-only Core snapshots while the native transport adapters are pending. The diagnostics panel should call CoreBridge contracts, including `ComputeTransportBindingDigestAsync`, and display errors if the native DLL is missing; it must not silently synthesize transport or suite results in C#.
- Keep the System Monitor workspace wired through `SystemMonitorWorkspaceClient` for explicit Windows runtime snapshots while ETW/EventSource sampling, GPU counters, thermal providers, helper installation, retention history, and alerting are pending. Disabled action buttons should stay visible so mac parity gaps remain obvious.
- Keep the Settings workspace wired through `SettingsWorkspaceClient` for explicit tabs/actions/details snapshots while persistence, import/export, permission prompts, reset, apply, restore defaults, and monitor-data deletion are pending. Disabled action buttons should stay visible so mac parity gaps remain obvious and high-risk writes stay explicit.
- Wire a Windows DNS-SD adapter behind `IDiscoveryBrowserClient` once network discovery is introduced. The live adapter should use Win32 `DnsServiceBrowse` to browse `_skybridge._udp` and `_skybridge._tcp`, resolve TXT records, pass those TXT records to `CoreDiscoveryClient`, and then hand `DiscoveredPeer.PublicKeyFingerprint` to `PairingMaterialClient` / the trust layer for verification instead of treating the fingerprint as a connectable public key.
- Wire the manual target output from `ManualConnectionClient` into future Windows endpoint hints only after discovery, pairing, trust approval, `CoreBridge.PlanConnectionAsync`, and transport binding are available. Manual Host/IP plus Code must not synthesize a `DiscoveredPeer`, capabilities, trust decision, or `IPeerPublicKeyProvider`.
- Wire the cross-network QR/code output from `CrossNetworkConnectionClient` into future signaling only after QR signature verification, expiry validation, the `DynamicQRCodeData` canonical verifier, trust approval, Core connection planning, and adapter transport binding are defined. `Generate QR Code`, `Scan QR Code`, `Generate Code`, `Copy`, `Regenerate`, and `Connect` must remain visible, but this boundary must not register a signaling room, start WebRTC offerer/answerer, open an HTTP file server, or call `FfiEngineClient`.
- Use `CoreBridge.SelectTransportAsync` / `skybridge_select_transport` to choose Apple-native, Windows MsQuic, WebRTC interop, relay, or TCP fallback plans from peer capabilities and path facts.
- Use `CoreBridge.ComputeTransportBindingDigestAsync` / `skybridge_transport_binding_digest` to bind the selected adapter, endpoint tuple, selected candidate pair, transport secret fingerprint, optional relay ID, timestamp window, and capability digest into one Core-owned transcript value before the session handshake accepts the transport.
- Keep `ConnectionPreflightClient` as the bridge from validated discovery/pairing material into Core readiness facts. It may compute a preflight digest to verify the FFI path, but live WebRTC/MsQuic/relay adapters must replace that placeholder binding material before any session transcript is accepted.
- Use `CoreBridge.MapChannelAsync` / `skybridge_map_channel` so Windows services consume Core logical-channel mappings instead of duplicating adapter policy in C#.
- Use `CoreBridge.PlanConnectionAsync` / `skybridge_plan_connection` for the pre-adapter contract that combines selected transport, selected crypto suite, offered suites, channel bindings, frame header size, and SBP2 policy.
- Use `CoreBridge.EncodeFrameAsync`, `CoreBridge.EncodeSbp2FrameAsync`, `CoreBridge.DecodeFrameMetadataAsync`, and `CoreBridge.DecodeFramePayloadAsync` so Windows WebRTC/MsQuic/relay adapters carry Core-owned `SBF1` frames and unwrap SBP2 through Rust instead of duplicating framing logic in C#.
- Use `CoreBridge.ParseDiscoveryAdvertisementAsync` / `skybridge_parse_discovery_advertisement` so Windows discovery consumes mac/iOS Bonjour TXT advertisements through the same Core validation path as the CLI.
- Use `skybridge transport select` for operator smoke checks against the same Rust selector before WinUI or native adapter wiring is available.
- Use `skybridge transport bind` for operator smoke checks of the Core transport transcript digest before MsQuic/WebRTC/relay adapters are wired.
- Use `skybridge channel map` to verify that each transport adapter uses channel-specific streams, datagrams, or DataChannels before real adapter wiring is enabled.
- Use `skybridge frame describe` to verify Core channel frame metadata and SBP2 padding flags before real adapter wiring is enabled.
- Use `skybridge connection plan` to verify the full Core-owned pre-adapter contract: selected transport, selected crypto suite, offered suites, channel bindings, frame header size, and SBP2 policy.
- Use `skybridge discovery parse` to verify mac/iOS Bonjour TXT advertisements and service names before Windows DNS-SD wiring is enabled.
- Use `skybridge suite offer` and `skybridge suite select` to verify provider-derived suite offers, remote wire ID parsing, and downgrade audit behavior before platform crypto provider wiring is available.
- Map engine callbacks (state changes, input responses) to UI updates via events or observable properties on the view model.
- Keep heavy work off the UI thread by continuing to use async commands for connect/heartbeat; the FFI layer should marshal any blocking calls to thread-pool threads when necessary.

## Testing approach
- UI logic remains in view models and services, enabling unit tests against `SessionViewModel` without a XAML runtime.
- UI parity tests should compare `FeatureEntryContract.Entries` against the macOS navigation order and automate shell selection before adding deeper feature pages. `Scripts/verify-windows-ui-parity.ps1` is the current text-only gate for navigation order, ordered top-bar parity controls, ordered workspace/action layout, shell bindings, Device Discovery scan controls, browser facts, manual target fields, cross-network QR/code controls, manual parser, pairing, connection preflight bindings, USB Management stats/device bindings, File Transfer queue/history/security bindings, Remote Desktop session/control bindings, Quantum/Core diagnostics bindings including transport binding digest visibility, System Monitor overview/detail/indicator bindings, Settings tabs/actions/details bindings, command bindings, and parity-document signals.
- Windows FFI client tests currently use `Scripts/verify-windows-ffi-client.ps1` as a text-only gate for `IEngineClient` coverage, required C ABI imports, explicit state refresh, CoreBridge discovery parsing, Windows DNS-SD browser boundary, manual connection target validation, cross-network QR/code schema, signature, expiry, and no-transport validation, pairing-material validation, connection preflight planning/binding/channel mapping, CoreBridge frame codec coverage, the modular `IDiscoveryClient` boundary, and the no-silent-default-switch rule.
- FFI glue is covered in Rust integration tests for engine lifecycle, transport selection, transport binding digest, channel mapping, frame codec roundtrip, and connection planning; Windows C# bindings should add text-only/interop tests once the WinUI test harness is introduced.
- Rust tests must cover transport selection defaults, channel reliability, transport binding digest changes, CLI/FFI binding digest exposure, and FFI selector contracts.
- Channel mapping tests must prove WebRTC uses distinct DataChannel labels, Windows MsQuic uses stream/datagram mappings, Apple native does not route Apple-to-Apple through WebRTC, and TCP fallback is visible as head-of-line blocking risk.
- Suite tests must prove unknown suite IDs fail closed, offered suites come from actual capabilities, classic/P-256 fallback is policy-gated, and timeout cannot trigger crypto downgrade.
- SBP2 tests must prove payload roundtrip, bucket selection, padding statistics, too-small target rejection, missing bucket rejection, bad magic rejection, and truncated frame rejection.
- Frame tests must prove plain and SBP2-padded frame roundtrip, version/magic/channel/flag validation, truncated payload rejection, FFI codec roundtrip, and CLI smoke coverage.
- Connection-plan tests must prove Windows-to-Apple interop selects WebRTC with distinct channels, Apple-to-Apple remains Apple native, unsupported peers fail closed, and timeout cannot create a classic crypto fallback plan.
- Discovery tests must prove `_skybridge._udp` and `_skybridge._tcp` service names remain stable, required TXT fields are enforced, `pubKeyFP` is exactly 64 lowercase hex characters, and macOS/iOS platform labels map to Apple capabilities without replacing Apple-to-Apple native transport.
- CLI smoke tests must launch the compiled `skybridge` binary and verify successful and failing basic commands. `Scripts/verify-rust-cli-coverage.ps1` is the Rust gate for this Windows parity branch: it runs `cargo test`, requires total line coverage to be at least 90%, and also requires `cli.rs` line coverage to be at least 90% so CLI reuse cannot regress behind broad Core coverage.
