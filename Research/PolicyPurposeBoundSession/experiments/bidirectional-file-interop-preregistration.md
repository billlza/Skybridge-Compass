# Bidirectional Physical-Product File Interoperability Preregistration

Status: preregistered experiment contract; no result is recorded by this file.

This protocol defines the first claim-eligible physical-product experiment for
the Policy-to-Purpose-to-Byte research line. It is deliberately limited to
bidirectional durable file transfer. A run is evidence only for the claims
explicitly named in its manifest; it does not update the claim ledger by
itself.

## 1. Research question and unit of analysis

The unit of analysis is one two-endpoint session attempt. The experiment asks
whether two physical product endpoints, built against one frozen
PolicyPurposeBoundSession commit, establish one authenticated BoundSessionV1
session over the actually selected WebRTC ICE pair and complete one durable
file transfer in each direction without changing either endpoint's trust
state.

The primary success condition is the conjunction of every gate in Section 4.
There is no partial-success interpretation. A failed or incomplete attempt is
retained under a new evidence identifier with `claim_eligible=false`; it is not
overwritten by a later rerun.

## 2. Evidence classes

The manifest field `evidence_class` has exactly three meanings:

- `diagnostic`: environment inspection, exploratory commands, or incomplete
  observations. It is never claim-eligible.
- `source_capability`: compilation, source conformance, simulator/emulator, or
  component-test evidence. It is never physical-product interoperability
  evidence and is never claim-eligible.
- `physical_product_interop`: a preregistered attempt involving exactly two
  physical product endpoints. It is claim-eligible only when the validator can
  establish every gate below from a locally complete, hash-bound evidence
  package.

Build success, source presence, a simulator, an emulator, a virtual machine, a
handshake, a DataChannel `open` event, or a file submission event cannot be
reclassified as physical-product success.

## 3. Pre-run freeze and collection plan

Before starting a run, the operator must:

1. Assign a new immutable `evidence_id` and record the UTC preregistration
   timestamp before the run start timestamp. The typed preregistration raw JSON
   must bind the run, contract ID, product scope, timestamp, and SHA-256 of this
   canonical protocol document; an arbitrary file with a valid hash is not an
   acceptable substitute.
2. Generate distinct, nonzero SHA-256 `run_binding` and `session_binding`
   correlation values before collection. Every ICE, PQC, transfer, durable
   commit/ACK, trust, and cleanup record for this attempt must carry both exact
   bindings. A record from another run or session is rejected even if its file
   hash is otherwise valid.
3. Freeze one 40-hex PolicyPurposeBoundSession commit. Both endpoint build
   records must name that same commit and must record a clean source tree.
   Platform product revisions may differ because they are separate products,
   but each revision and final binary is independently bound in the manifest.
4. Record the two physical endpoint classes using the SHA-256 digest of a fresh,
   random, run-scoped pseudonym generated by the collection harness. Do not hash
   a stable hardware identifier. Raw UDIDs, serial numbers, account identifiers,
   IP addresses, tokens, and credentials must not enter the evidence package.
5. Capture a semantic trust-state snapshot on each endpoint before connection.
   The snapshot must include the authority epoch and trust-record count used by
   the product verifier.
6. Prepare two distinct, nonempty payloads, one for each direction. Their
   SHA-256 digests must differ. Record the exact byte count and digest before
   transmission.
7. Configure raw capture paths before the run. Every manifest artifact is a
   canonical relative path below one evidence root and is re-hashed by the
   validator. Raw build, device, ICE, PQC, transfer, durable, trust, and cleanup
   JSON is parsed under closed schemas and compared field-for-field with the
   manifest. Symlinks, hard-link aliases, parent traversal, non-regular files,
   and files that change while being read are rejected.

Typed raw JSON records, including the preregistration record, are capped at
256 KiB, each binary or file payload at 1 GiB, and the complete declared
package at 4 GiB. The validator opens path components through no-follow
directory file descriptors, checks the opened regular file with `fstat` before
reading, hashes that descriptor, and checks the same descriptor again
afterward.

SHA-256 is used here to bind exact file and evidence bytes and to detect
accidental corruption. It is not device attestation and does not protect
against a malicious evidence producer. No additional signature, MAC, or
encryption mechanism is introduced by this artifact contract.

## 4. Claim-eligibility gates

A run may set `claim_eligible=true` only when all of the following are true:

1. **One run/session:** the manifest and every runtime/effect raw record carry
   one exact run binding and one exact session binding. Neither cross-run nor
   cross-session evidence may be spliced into the package.
2. **Frozen source:** both build records name the same frozen evidence-root
   commit; both source trees are clean; each binary and build record is present
   and hash-valid.
3. **Physical endpoints:** exactly two distinct endpoints ran as physical
   devices, with device records and final binary records present.
4. **Selected transport:** both endpoints report the selected, succeeded ICE
   candidate pair for the same correlation digest. The selected pair identifier
   and local/remote candidate types are not `UNKNOWN`; a merely nominated,
   checking, failed, or unreported pair fails the gate.
5. **PQC session:** both endpoints report an authenticated `bound-session/1`
   session using Q-Periapt ABI2 PolicyBound (`suite_id=0x0012`) with
   `ML-KEM-768+X25519`, hybrid profile 2, and the same nonzero session-binding
   digest. Classic or unspecified suites fail the gate.
6. **Bidirectional exact bytes:** there are exactly two transfers, covering the
   two opposite ordered endpoint pairs once each. Each payload is nonempty and
   the two payload digests differ. For each transfer, sender and receiver byte
   counts and SHA-256 digests match, and the validator re-hashes the retained
   source and receiver files to those values.
7. **Durable authenticated ACK:** for each direction, the receiver reports a
   durable storage commit before issuing an authenticated ACK. The ACK repeats
   the exact byte count and content digest, uses the BoundSessionV1 effect
   receipt protocol, names one closed durability-primitive class, and has
   separate commit and ACK raw evidence. Sender completion or receiver memory
   buffering is insufficient.
8. **Trust-state preservation:** each endpoint has before and after evidence;
   semantic state digest, trust-record count, and authority epoch are identical,
   and `unchanged=true`.
9. **Owned cleanup:** both endpoints terminate the session and release their
   own resources only after validating the recorded owner binding. Cleanup must
   report `owner_verified_and_released`, must cover both endpoints, and must
   report that no foreign resource was touched.
10. **Complete artifact root:** every declared artifact is used by the manifest,
   every referenced artifact has the expected kind, and path, byte count, and
   SHA-256 are verified from disk.
11. **Closed schema and raw correspondence:** the validator executes the
   committed Draft 2020-12 JSON Schema, rejects undeclared properties and
   unsupported schema keywords, then parses every typed raw JSON record and
   requires exact correspondence with the manifest fields that cite it.

The validator's acceptance is a necessary artifact-structure check, not proof
that an operator, operating system, or endpoint honestly reported an event.
Independent reproduction and the broader claim-ledger requirements remain
separate gates.

## 5. Procedure

1. Verify the frozen commit and clean build inputs; install the recorded binary
   on each preregistered physical endpoint.
2. Capture both pre-run trust-state snapshots.
3. Start exactly one product session and retain the authenticated BoundSessionV1
   suite reports from both endpoints.
4. After ICE selection, capture the selected candidate-pair report on both
   endpoints. Do not substitute signaling reachability, connection state, or a
   candidate list for selected-pair evidence.
5. Transfer payload A from endpoint A to endpoint B. After the receiver's named
   durable-storage primitive completes, capture the authenticated durable ACK
   and retain the received file.
6. Transfer the distinct payload B from endpoint B to endpoint A under the same
   rules.
7. Capture both post-run trust-state snapshots.
8. Close the session through the owner-bound product path. Capture one cleanup
   record per endpoint and verify that no unrelated session or resource was
   touched.
9. Finalize the manifest without modifying raw artifacts, then run the
   validator against the evidence root.

From `Research/PolicyPurposeBoundSession`, the validation entry points are:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 artifact/validate_experiment_evidence.py \
  /path/to/evidence/manifest.json \
  --artifact-root /path/to/evidence

PYTHONDONTWRITEBYTECODE=1 python3 -W error -m unittest -v \
  artifact.test_validate_experiment_evidence
```

## 6. Failure and negative-control rules

Any missing, ambiguous, rejected, unauthenticated, mismatched, or stale value
sets `claim_eligible=false`. Unknown ICE data, a classic suite, one-way transfer,
non-durable ACK, changed trust state, or unverified cleanup ownership is a failed
gate, not a reason to infer a fallback success.

Before using the contract for a paper result, clone a valid test manifest and
individually mutate at least the frozen commit, physical-device class, ICE pair,
suite, run/session binding, reverse transfer, zero-byte payload, equal payload
digests, byte count, content digest, durable ACK, trust state, cleanup ownership,
raw-record contents, undeclared JSON properties, artifact size, and artifact
digest. Each mutation must be rejected by the validator tests.

## 7. Claim boundary

This v1 experiment may support only:

- `BS-FILE-DURABLE-RECEIPT`;
- `BS-APPLE-PHYSICAL-E2E` when both endpoints are Apple products; or
- `BS-NONAPPLE-INTEROP` when one endpoint is Apple and the other is non-Apple.

It does not establish formal security, hostile-caller isolation, binary
constant-time behavior, publication readiness, or the global immutable
evidence-root claim.

Remote desktop and messages are explicitly `not_claimed`. In particular, an
Android-to-iOS or iOS-to-Android file-transfer run must not be described as
Android/iOS remote-desktop or message interoperability. Those product effects
need separate preregistration, purpose-specific trusted committer semantics,
raw effect evidence, and a new contract revision. No such result is asserted or
fabricated here.
