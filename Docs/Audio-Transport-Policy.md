# 音频连接方式与质量策略

日期：2026-10-20。状态：用户需求已确认；传输适配与设备验收仍在实施。
关联：[音频消息契约](Audio-Streaming-Contract-v1.md)。

## 已确认的产品目标

提供有线和无线播放。USB、Wi-Fi 保留原样文件/样本的目标；蓝牙允许合理的有损压缩，以正常使用范围内连续、稳定、没有异常声音为优先。蓝牙兼容策略不得自动扩散到 USB 或 Wi-Fi 严格模式。两类音源仍同等重要：可读取音乐文件与系统允许捕获的应用声音。

入口沿用“设备 → 在此设备播放”。同一播放页选择“自动 / USB / Wi-Fi / 蓝牙”，展示实际正在使用的链路与质量状态。未实现或当前设备不支持的方式明确不可用。仅有线缆、设备发现或底层蓝牙连接成功，不等于已认证音频会话。

| 方式 | 目标 | 模式边界 |
| --- | --- | --- |
| USB | 稳定、高带宽、本地原样播放 | 承载原始文件/PCM；仍受源捕获与输出设备能力限制 |
| Wi-Fi | 无线原样播放 | 区分局域网直连、热点直连和真正的 Wi-Fi P2P；实际链路不能靠名字推定 |
| 蓝牙 | 便携、稳定、允许压缩 | 单独协商压缩编码、码率、缓冲及输出处理，不展示无损标记 |

自动模式优先满足当前质量承诺，再在实际可用链路中选择。链路切换必须绑定同一协议身份并重新验证当前授权，建立新 stream owner，隔离旧数据；选择严格模式时不能静默退到有损蓝牙。失联不能通过继续显示“播放中”掩盖。

用户已再次确认：即使当前 Mac 输出的只读能力声明不足以满足严格策略，也保持严格模式，待兼容输出设备后再播放；不增加或自动切换到系统混音兼容播放。只读能力快照与实际独占初始化分开记录，不能将独占前未见 nonmixable 格式直接升级为“硬件已证不支持”。

2026-10-20，用户确认目前没有可用于验收的 USB 声卡／DAC。兼容输出设备上的严格原格式播放保持未验收；授权、协议和模拟器回归不能替代这项硬件证据。

## 已确认的离线授权要求

已完成账户设备授权和配对的两端，在已有授权有效期内，USB / 专属 Wi-Fi 必须能够不依赖互联网播放。音频数据连接、账户设备授权、接收端本次播放许可分别检查；在线状态图标和历史配对本身不能发放账户授权。

首次取得或续期授权需要受认证的账户查询，绑定实际握手的双方设备 ID、签名算法及公钥指纹，以及账户 authority / tenant / user。完整设备列表必须明确显示双方为 active。在线查询失败时，已有且仍有效的本地授权可以继续使用；没有有效授权则明确要求联网验证，不能用显示缓存、presence TTL 或默认允许替代。

授权有效期从取得证据的请求开始计算；新连接、切换链路、重复读取缓存和 JWT refresh 均不得重置期限。每个播放流仍有独立 owner 和接收许可。普通 access token 自然到期与退出账户不是同一事件：前者阻止新的在线请求，后者必须立即撤销本地音频授权。账户切换、已观察到的设备撤销和协议身份变化同样失效；退出再登录同一账户也不能复活旧授权。

完全离线期间无法立即获知服务器上的远端撤销；既有授权只持续到原截止时间，恢复联网后复核并处理撤销。界面应显示“离线授权有效至……”以及实际连接方式，不能显示已实时向服务器确认。实现还需要受保护的本地存储和明确的重启/时钟回拨策略，不能将普通偏好设置中的时间戳当作可信凭据。

当前授权为不可从对端解码的本地 membership evidence 和有限租约，工程上限暂为一小时；这不是服务器签发的离线证书，也不是用户已选择的最终时长。各平台的受保护恢复与播放集成进度如下；组件测试通过不能标记“离线播放已可用”。

Mac 的 `AudioAccountMembershipProvider` 与 iOS 的 `IOSAudioAccountMembershipProvider` 已接入受保护的授权检查点。iOS 将检查点与登录标识、撤销状态和请求记录保存在原有应用私有 Keychain 条目中；启动见证只标识单调时钟所属的系统启动，不含账户权限。同一次系统启动内，应用退出再打开可恢复尚有效的原授权，不能延长截止时间；系统重启或启动见证丢失后淘汰旧检查点，须联网重新验证。现行实现不承诺跨系统重启的离线授权恢复。组件及原生存储证据见下文，Keychain 中仍有登录凭据不等于实际离线播放已验收。

2026-10-19，Mac 接收会话已接入自动续期：仅在本次播放批准后启动，绑定原账户、登录世代、连接 owner、双方协议身份和同一租约。新查询结果须先持久化，再交接给该播放；不会批准另一首音源或另一条连接。默认在原授权到期前 120、75、40 秒尝试，单次总时限最多 35 秒并受原到期时间约束；较晚进入的播放不会连发已错过的重试。显式离线的续期运行不发请求。只在受认证请求边界重试明确的暂时网络／服务故障；本地缺少 refresh credential 不视为服务器撤销，仍仅保留旧授权原有效期。保护存储失败、身份不符、TLS 失败和已观察到的撤销均不能作为网络故障放行。

续期任务由播放会话取消和回收；停止时先关闭音频输出，再等待账户请求退出，超时或不合作的请求不能保留输出或复活旧会话。界面显示续期状态及实际提交后的授权截止时间。共享调度与 Mac 音频边界通过 132 项定向回归，登录／令牌刷新边界另通过 28 项回归；测试使用受控账户数据，未验证真实服务的一小时边界或真实长时间播放。该阶段证据为 Android 工作区 `experiments/audio-preservation/results/2026-10-19/apple-session-renewal-v2`。

2026-10-20 的受控反例发现：设备列表已报告对端被移除，但负面检查点写入失败时，进程内虽然撤销了租约，新建的 Mac provider 仍能从最后一次成功保存的记录恢复旧授权。旧行为的一个 XCTest 用例失败，原始日志和输入保留于 Android 工作区 `artifacts/apple-audio-observation-20261020/restart-counterexample-01.log`；该反例使用实际共享存储／Mac provider 与受控写入故障，并非真实 Keychain 故障或实际进程终止。

Mac 现将凭据刷新，以及已发布音频账户世代的设备列表、心跳、移除和播放授权查询的请求标记写入同一个受保护账户记录，准备成功后才允许进入请求。未持有音频账户世代的普通设备请求继续与音频授权分离，不能借用稍后发布的世代。每个标记绑定本次登录与请求，最多保留 32 个；只能由原请求结算，旧请求不能清除新请求的标记。新授权和自身标记的结算通过一次条件写入提交；负面观察立即撤销内存租约，负面检查点保存成功后才能清除自身标记。保存失败、未知中断或丢失移除回执时保留未结算记录；新实例不能恢复旧检查点。明确的临时只读请求失败可以结算，但不改变原授权内容和到期时间。移除请求的网络失败不能当作只读离线失败处理。

受保护记录格式从版本 1 迁移到版本 2；原登录标识和凭据保留，旧格式或中断的凭据验证必须先重新验证，不能靠设备查询解除凭据验证状态。新验证会先淘汰不确定的旧音频检查点；新授权仍须来自完整、受认证的设备查询。普通有效凭据刷新不会延长已有音频授权。共享请求记录也绑定其创建的 store 实例，并在请求边界结束时失效；补测曾复现结束后重复使用和跨实例使用的两个反例，修复前的四项失败断言保留在 `request-owner-red/`。该请求记录阶段的 iOS 已适配相同请求边界，但当时仍使用内存授权；后续持久化接入见下文。

账户请求记录阶段的定向检查为 244 项 Mac XCTest（另有三项 Swift Testing）及 188 项 iOS 27 模拟器 XCTest，均零失败、零跳过，记录中的源码输入在检查期间未变化。Mac 保留已有的 duplicate-rpath 链接警告；模拟器结果包没有编译问题或 XCTest 运行期警告，其系统网络取消诊断在此前日志中也存在。最终 iPhoneOS 原生构建结果与未验证边界见同目录 `result.json`；本阶段不将组件检查记为真实账户、物理输出或真实 Keychain 故障恢复的验收。

2026-10-19，iOS 原文件发送器在电脑接受文件后启动共享续期，系统声音发送器在电脑接受且确认精确输出格式后启动。续期只更新同一个账户租约；各次请求前后仍核对原连接与租约对象。停止时先取消采集／关闭文件及连接、通知电脑，再等待续期请求退出；不能由未及时返回的请求保留音源或复活发送。两种入口显示实际授权截止时间及续期状态。自然过期的本地 JWT 现在单独分类：仍不允许带过期凭据发出新请求，但不会据此把旧有限播放授权视为服务器撤销；损坏声明、TLS、存储和已知撤销错误保持失败。账户设备页对这种自然过期显示重新登录提示，不显示内部错误码。

`ios-session-renewal-v1` 的现有专用 iOS 27 模拟器通过 188 项不同回归用例，包括新增 9 项；增强续期呈现后复验了相关既有用例，未将重复运行算作新增覆盖。Xcode 结果包记录零失败、零跳过、无运行期警告；原生截图核对了续期状态、原格式信息与停止操作的布局。最后的 Xcode 27.1／iPhoneOS 27.1 完整无签名构建通过，1,653 个输入未在构建中变化，编译无错误或警告，未安装到物理设备。首次测试编译的闭包类型推断错误及修复记录均保留。真实服务的一小时边界、持续物理播放、iOS 重启后的受保护授权恢复、Windows 接收器自动续期仍未完成；这些组件结果不能替代手机到电脑的播放验收。

Apple 的 [iOS / iPadOS 18 发布说明](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-18-release-notes)明确移除了应用对 `kern.bootsessionuuid` 的访问，因此不能把 Mac 的该适配器复制到 iOS，也不能以临时随机 UUID 或仅凭墙上时钟推算的值代替启动会话标识。iOS 恢复方案必须先验证公开可用的时钟语义，再与持久登录身份、原截止时间和原子撤销一起接入；未完成前保留此验收缺口，不延长原授权期限。SensorKit 的 SDK 头文件虽描述了跨睡眠和重启的 `SRAbsoluteTime`，但其普通应用适用性仍未确认，[官方配置说明](https://developer.apple.com/documentation/sensorkit/configuring-your-project-for-sensor-reading)要求研究项目授权；本次没有添加该依赖、读取传感器或修改签名能力。

2026-10-20 的 iOS 反例分别复现了正常恢复创建新登录标识、音频授权撤销后新建状态管理器又恢复授权的行为。iOS 现复用 `ProtectedAccountSessionStore`：凭据、稳定登录标识、撤销状态与待结算请求同处一个 Keychain 记录；正常恢复及已验证刷新保持登录标识，明确的新登录仍创建新标识。退出写入永久拒绝旧凭据回退的空会话记录。只有新版命名空间不存在时才迁移原格式，已建立的记录即使清空也不会回读旧凭据；原格式清理失败显式报告，可在之后重试清理。

刷新请求须先成功写入待结算标记，再进入 HTTP；本次响应通过验证后，将新凭据与标记结算一并提交。进程丢失请求所有权、未知中断、保存失败或确定的服务器拒绝，均不能在新实例中恢复旧音频授权。只有已有所有权的明确临时请求故障可以结算，且不会将未知前序请求变成已验证。新登录、取消和晚到请求继续服从原会话所有者检查；已提交的刷新不会因提交后的等待者取消而丢失发布。登录显示与音频准入保持分离，待验证的账户在下次信令请求时自动要求凭据验证。

iOS 新记录与旧格式迁移明确限定应用自身的 Keychain 访问组；保持 `AfterFirstUnlockThisDeviceOnly`、禁止同步，不新增共享凭据权限。依据 [Apple 的访问组定义](https://developer.apple.com/documentation/security/ksecattraccessgroup)，未指定访问组的查询会覆盖所有可访问组，因此迁移不使用这种宽泛查询。原生 Keychain 的实际设备迁移、设备锁定及真实应用终止恢复仍待 iPad 验证；当前模拟器结果仅覆盖其自身的 Security.framework 与受控故障注入。阶段证据目录为 Android 工作区 `artifacts/ios-durable-auth-20261020`。

本阶段最终 264 项 iOS 27 模拟器 XCTest 全部通过，零失败、零跳过，结果包无运行期警告；其中使用真实模拟器 Security.framework 的独立临时条目验证了条件写入、撤销、空会话记录和清理。旧实现的两个反例实际失败，修复后通过。原生 iPhoneOS 27.1 Debug 构建也通过，编译无错误或警告；两次接受检查期间源码输入均未变化。设备构建使用 `CODE_SIGNING_ALLOWED=NO`；首次无签名构建未展开 `AppIdentifierPrefix`，随后从既有描述文件核实前缀并作为该次构建参数显式传入，最终包的应用私有 Keychain 组与描述文件一致。此包尚未签名，也未安装到 iPad，不能据此确认真实设备迁移、首次解锁、应用终止或离线播放已通过。首次编译发现的新错误类型分类遗漏及其修正保留在同一证据目录，最终结论以 `result.json` 为准。

2026-10-20 的隔离时钟探索增加了应用专属的 POSIX 命名共享内存候选：Apple 的 [shm_open 文档](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/shm_open.2.html)说明对象可跨进程保留，但不会跨系统重启保留。其随机标识仅用于识别同一次启动中的单调时钟来源，不能携带或签发账户授权；对象丢失时旧检查点失效。初始化采用有界进程锁、一次提交和明确的损坏失败，正常退出不删除对象。首轮探针因内核按页分配而失败，已根据 Apple XNU 实现和实际返回值修正大小检查，原失败保留。

此候选在 Mac 的真实进程／内核上通过八项检查，包括并发、实际终止初始化进程和损坏拒绝；系统重启仅模拟对象丢失，未真实重启。它尚未进入产品路径。现有 iOS 签名包没有 App Groups entitlement，尽管配置描述文件已允许目标组；Keychain 共享权限不能代替 POSIX IPC 所需的 [App Groups 能力](https://developer.apple.com/documentation/xcode/configuring-app-groups)。该轮 iPad 不便接入，因此当时没有 iOS 沙盒、真实应用重开与系统重启的证据。Mac 实验保留于 Android 工作区 `artifacts/ios-audio-boot-witness-20261020/native-results.json`。

同日 iPad 通过 USB 重新接入后，使用既有签名身份、应用标识和权限完成原生补测。iPadOS 27.0.1 的真实 Data Protection Keychain 通过条件写入、撤销、空会话记录和清理检查。随后以同一隔离合成账户，分四次启动实际应用测试宿主：迁移旧条目；在新进程中确认原登录标识保持并写入未结算凭据请求；再次启动确认音频账户授权不能恢复，再退出并故意留下旧格式条目；最后启动确认空会话记录阻止旧条目复活并清理夹具。四次 PID 均不同、四阶段均通过；每阶段的回执和前置断言保留。存储与状态管理使用生产实现，Keychain 命名空间和旧条目的读写注入仅用于隔离合成数据，不接触真实账户、不发送 HTTP、不播放音频。

时钟候选的原生沙盒前置检查则实际失败：`shm_open` 和 `kern.bootsessionuuid` 的尺寸查询均返回 `EPERM`。这是当前签名权限下的明确拒绝，不能推导为所有 App Groups 方案均不可行，也不能将单调时间戳本身当作跨重启身份。本轮没有增加 App Groups 权限、使用受限 API 或启用持久音频检查点。失败断言、JSON 附件和隔离 C 包装层保存为研究证据；临时探针已从常规 XCTest 源撤出，重启恢复夹具作为回归资产保留。

## 现有代码与平台边界

Mac 接收服务启停现在会通过既有加密 `pairingIdentityExchange` 更新已准入连接的音频能力。异步身份准备结束后，在同一 MainActor 执行段读取当前能力并提交消息，连接关闭时取消其更新任务。2026-10-18 的 139 项定向回归通过，其中同一条真实本机 TCP 连接验证了能力撤回与恢复；身份和会话密钥来自受控测试输入，尚不代表手机界面、真实配对或播放验收。证据目录为 `apple-audio-capability-refresh-v1`。

### Mac 蓝牙的现状

`Sources/SkyBridgeCore/Device/BluetoothManager.swift` 当前使用 `CBCentralManager` 进行 BLE 扫描、连接与列表更新。`connect(to:)` 发起连接；`didConnect` 更新设备列表。本文件没有 GATT 特征读写、L2CAP 音频数据通道、SkyBridge 对端握手或音频播放器，因此现有“蓝牙已连接”不能直接转化为音乐接收。

可探索的产品数据通道是 BLE L2CAP CoC：当前 macOS SDK 公开 `CBPeripheralManager.publishL2CAPChannel(withEncryption:)` 与 `CBPeripheral.openL2CAPChannel`，Android API 29 起公开 `createL2capChannel`。这些提供字节通信基础，不提供账户身份、SkyBridge 音频许可或吞吐保证。必须在其上复用现有签名身份与会话加密，而不是信任广播名称或蓝牙地址。[Android L2CAP](https://developer.android.com/reference/android/bluetooth/BluetoothDevice#createL2capChannel(int))、[Apple L2CAP](https://developer.apple.com/documentation/corebluetooth/cbperipheralmanager/publishl2capchannel(withencryption:))

蓝牙也可用于发现与协助建立 Wi-Fi 连接，但用户已明确允许蓝牙自身承担压缩音频；不能仅以遥控功能代替这一目标。Bluetooth SIG 的 HLC 页面本次查询仍标记为 draft；HDT 官方资料描述未来更高的数据率，不证明当前手机、Mac、Windows 的硬件和公开 API 已支持。实现以实际两端协商与实测为准。[HLC](https://www.bluetooth.com/specifications/specs/high-resolution-lossless-codec/)、[HDT](https://www.bluetooth.com/blog/bluetooth-le-will-soon-get-a-major-boost-in-speed-introducing-bluetooth-high-data-throughput-hdt/)

### Wi-Fi P2P 不能跨平台按同名 API 推定

Android 的 Wi-Fi Direct 要求双方的硬件/系统支持相应 P2P；Wi-Fi Aware 是另一套 NAN 发现与数据路径。Apple 的 `includePeerToPeer` 使用 Apple 的对等 Wi-Fi 协议，官方说明其线协议未向第三方开放、用于 Apple 设备之间；它不是 Android Wi-Fi Direct 的通用接收端。[Android Wi-Fi Direct](https://developer.android.com/develop/connectivity/wifi/wifip2p)、[Apple 网络 API 选择](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api)

当前 Mac 的 `WiFiAwareDiscovery.swift` 实际是 `MCNearbyServiceBrowser` 被动浏览器，没有建立 NAN 数据连接。本机 Xcode SDK 的 `WiFiAware.swiftinterface` 将 `WACapabilities` 标为 `@available(macOS, unavailable)`；Apple DTS 的说明也区分 framework 存在与 Mac 真正支持 Wi-Fi Aware。因此 Android→当前 Mac 不能直接以已有同名类宣称“标准 Wi-Fi Aware 直连已支持”。[Apple DTS](https://developer.apple.com/forums/thread/827887)

第一条实际链路应沿设备页已有、已认证的 LAN 连接接入音频。独立热点与标准 Wi-Fi P2P 的可用组合另做适配及实测；不把普通局域网连接标成“无需路由器的 Wi-Fi Direct”。Wi-Fi 音频数据默认直接在所选设备之间传输，不能仅因使用 WebRTC 就推断走互联网或中继，也不能凭 API 名称推断没有中继。

### USB 的现状

Mac 已有 `USBMultiplexTransport.swift`，通过系统 `usbmuxd` 的同一连接承载已有协议，并明确排除 Network 设备条目；`P2PDiscoveryService.connectOverUSB` 进一步执行原有身份握手。下述 iPad 原文件验收复用了此路径；它不适用于任意 Android 手机，也不单独证明音频输出成功。

2026-10-18 的独立真机实验确认：当前 iPad Pro 11-inch (M4) 上仅绑定 `127.0.0.1` 的 `NWListener` 可以接受 Mac 经系统 `usbmuxd`、精确选择 USB 设备后建立的连接，并在同一条流上向 Mac 回传 2 MiB 合成数据。全部字节与 SHA-256 一致；Mac 观察到 EOF，iPad 记录了确认回执以及监听器/连接的取消完成，并通过独立容器文件读取核对。实验未替换正式应用，临时探针已移除。证据目录 `ios-usb-return-stream-native-v1/attempt-181235`，证据清单 SHA-256 为 `b7c783ded7a5930f818d61a53c0e7c4ae7ba139c1c0d19a3a64b0cac809b502c`。这只证明该物理组合的返回流能力，不证明账户认证、音频文件协议、独占输出、持续播放或拔线恢复。

iOS 原文件发送器现明确区分网络直连与 USB 返回流。USB 需要两端在已提交的配对信息中声明对应能力：手机收到本次文件接受消息后创建一次性本机监听器，Mac 按当前会话绑定的精确 USB 设备拨号，再复用现有元数据 MAC、接收批准、分块加密和摘要回执。音频 offer、连接代际、账户有效期和本次播放许可继续逐一验证；选择 USB 后不会改走普通网络文件入口。音频页显示所选文件传输方式。134 项 Mac 定向回归和 66 项 iOS 27 模拟器回归已通过；真机原文件传输结果见下段，严格播放和手机文件选择器的 USB 流程仍待验收。

2026-10-18 的产品真机验收在当前 iPad Pro 11-inch (M4) 与 Mac 上建立了 `Q-Periapt-ABI2-PolicyBound` USB 会话，使用真实账号授权和 Mac 的单次播放批准。独立 Debug 音频入口只生成固定的 1 秒、48 kHz／24-bit／双声道 WAVE 样本，不预置信任、账号证据或密码学策略。正式发送器收到原文件的认证回执：288,068 字节，SHA-256 `3832fe3f7365866fb48e624caedbfe0d04661f189253e26a9730b91824c4c328`；独立重建样本得到同一摘要。随后 Mac 在 `preparing` 阶段以 `unsupportedOutput` 拒绝内置扬声器，未报告播放完成。iPad 确认源句柄及文件连接关闭，容器回读确认测试音频已删除；Mac 私有接收目录和相关打开文件句柄均为空，主 USB 会话仍通过认证。iPad 已恢复普通启动并再次通过同一 USB 身份验证。证据目录 `ios-usb-original-file-product-v1`。这证明本机组合的原文件 USB 数据链路与失败清理，不证明文件选择 UI、FLAC 真机 USB、持续／后台播放、Windows USB 或兼容 DAC 的原格式输出。

同日的 `mac-audio-output-diagnostics-v1` 修复了输出拒绝后音源格式丢失的问题：来源 PCM 元数据独立于输出准入保存；本机界面区分格式不匹配、混音、声道布局、独占占用等已知原因，远端仍只收到原有 Stop 类型。旧实现的 WAVE／FLAC 回归均复现格式为空，修复后的 107 项定向回归通过。再次使用真实账号、USB 会话和单次播放批准传输上述固定 WAVE，认证摘要仍一致；当前内置扬声器的实际初始化错误明确为 `output.format_mismatch`，界面保留 48000 Hz／双声道／24-bit 整数格式，未宣称输出已就绪。iPad 源和文件连接关闭，测试音频已删除，Mac 私有文件及打开句柄为空；iPad 恢复普通启动后再次完成 USB 认证。首次请求在尚未点击批准时超时，首次恢复连接也被拒绝，两次原始失败均保留。后续签名身份探测及一次有界重连成功；尚未确定首次恢复拒绝的具体原因。本轮没有改变严格输出条件，也不构成可听播放或 DAC 验收。

`apple-usb-reconnect-readiness-v1` 随后复现并定位了两个冷启动边界：应用进程启动时控制端口可能尚未绑定；即使原生监听器已接收连接，iOS 的 Bonjour 注册仍可能未结束，旧实现会以 `listener-not-active` 拒绝它。Mac 现在仅在发送应用协议数据之前，对 usbmuxd 的连接拒绝执行共享 5 秒截止时间、最多 16 次的有界等待；设备丢失、无效响应和协议错误不进入此恢复。iOS 将临时连接绑定到本次监听启动任务，沿用既有连接容量、首帧期限和取消所有权，启动成功后才开始协议处理。原生返回码依据 [libusbmuxd 协议定义](https://github.com/libimobiledevice/libusbmuxd/blob/master/include/usbmuxd-proto.h)。

该修复通过 120 项 Mac 回归和 110 项 iOS 27 模拟器回归；后者包含六项启动等待、失败、取消及代际隔离检查。最新 iOS 包额外增加了只读 Debug 音频就绪诊断，原生构建、签名及真机运行通过；诊断追加后未重跑模拟器测试。修复后的三次冷启动连接（一次诊断启动、两次普通启动）均在首次请求中完成同一指纹的 `Q-Periapt-ABI2-PolicyBound` USB 认证。真机轨迹直接记录到连接等待监听启动后进入协议处理。再次传输固定 WAVE 时认证摘要一致，严格输出仍拒绝当前扬声器，两端资源及临时文件清理通过；最终已恢复普通启动。

此阶段仍保留一次已认证会话上的 `targetUnavailable`，发生在创建音频文件之前。追加诊断后的成功试验显示，配对和身份绑定有效时，接收端能力会从仅捕获更新为原文件及 USB 返回流可用；它不能反推此前失败的具体原因。当时尚未完成 Mac 配对回复节流与音频能力发布时序的确定性复现，后续验证见下段。当时设备发现页会将实际 USB 连接与 Wi-Fi 发现标签并排呈现，USB 管理页也未呈现已有会话；后续界面修正见下文。CLI 传输证据不能代替产品界面验收。

2026-10-19 的 `apple-audio-pairing-readiness-v1` 确定性复现了一个能力漏发路径：同一设备的身份信息已记录，但第一次交换尚不能提交音频通道；后续当前会话完成音频准入时，回复仍被 10 秒重复消息节流拦截。受控 Finished／身份输入配合真实本机加密 TCP、生产运行时提交及发送路径，旧行为出现两项断言失败，第二次发送字节数没有增加。修复后，首次音频准入触发一次能力发布，已准入的相同交换仍被节流；缺少当前操作序号、旧操作、不同会话密钥或身份不匹配不会获得 USB 音频能力。102 项相关回归通过，包含身份提交、握手所有权、能力发布和 USB 边界。

该修复版 Mac 与现有 iPad 原生包完成首次 USB 认证，iPad 记录到原文件与 USB 返回流能力从不可用变为可用，随后取得固定 WAVE 的一致认证摘要。Mac 仍拒绝不匹配的内置输出，资源与临时文件已清理，iPad 恢复普通启动后首次连接再次通过。此结果证明该可达漏发缺陷已修复及本机传输回归通过；此前缺少完整状态记录的 `targetUnavailable` 尚不能唯一归因于该缺陷，也未证明长期运行、所有链路或实际可听输出。

同日 `usb-connection-presentation-v1` 将当前控制链路从连接 owner 发布到临时 presence 快照。设备行按协议标识匹配当前会话，不再用同名或相同 IP 借用连接信息；已连接时显示“USB 已连接”或“网络已连接”，未连接时将 USB／Wi-Fi 等标签明确标为发现方式。更换 owner 时，缺失的网络文件地址会清除旧会话地址；旧 owner 的回调不能覆盖新链路。USB 归因记为 `usbDirect`，不计入网络中继占比。

USB 管理页会读取当前精确线缆绑定的已认证会话。尚未连接时，只读签名探测可预选同一指纹的已配对设备，不创建信任或自动连接；设备标识收进详情。161 项回归通过；真机界面从无已认证连接开始，自动选中 iPad，点击一次“连接”后显示 USB 已连接，设备发现页与 CLI 的 USB 结果一致。iPad 普通启动恢复后重新打开 USB 页面也保留正确状态。原文件回归仍取得上述 WAVE 的认证摘要，严格输出拒绝和资源清理正常。硬件清单中的 MFi 误分类、缺失翻译及旧的待验证配对记录仍有单独的修正工作，不能用本阶段结果宣称整个设备管理体验已完成。

该接收器的 `purpose: .originalAudio(transfer)` 要求注册表中的音频传输对象与调用方持有的批准对象完全相同；缺失、被替换或文件 ID 不匹配时拒绝接收。此入口还要求经过元数据认证的 `classic_approval_v1`，并拒绝进入普通文件恢复流程。2026-10-18 的接收边界阶段通过 112 项定向回归，包含六个真实本机 TCP 用例；证据目录为 `apple-audio-file-purpose-v1`。随后接入 USB 适配与可选 opcode 17，证据目录为 `apple-usb-original-file-v1`；旧版手机、不具备精确 USB 绑定的连接和未安装接收服务的设备仍不发布 USB 原文件能力。

Android USB 需要单独评估 AOA 数据 bulk 或真实 USB 网络接口的产品适配。不要使用已经在 Android 8.0 弃用、且限制为 44.1 kHz/16-bit/stereo 的 AOAv2 音频输出去冒充原样通道。AOA 的一般数据通信与那条旧音频接口不同；还需验证手机 accessory 支持、电脑 host API、系统授权、枚举/重连和拔线清理。[Android USB accessory](https://developer.android.com/develop/connectivity/usb/accessory)、[AOSP AOA 2.0](https://source.android.com/docs/core/interaction/accessories/aoa2)

普通用户的有线功能不能以开启 ADB/开发者模式作为交付前提。iOS→Windows 的 USB 驱动和宿主路径仍须单独验证，不能拿 Mac 的 usbmuxd 源码当成 Windows 已完成。

## 蓝牙压缩模式的工程要求

1. 单独协商真实支持的编码器/解码器和参数。现有 Opus 组件是候选复用点；不能把 Opus 字节塞进 v1 `pcmData` 并仍按原始 PCM 校验。编码参数、源格式、传输格式与实际输出格式分别记录。
2. 有界预缓冲与抖动缓冲；按接收播放时钟调度，避免直接用无线消息到达时间驱动输出。蓝牙模式可显式使用时钟漂移补偿，严格模式保持其原有承诺。
3. 根据实际吞吐、排队时延和缓冲水位调整码率/缓冲；不根据 RSSI 单独推断可用带宽，不以未测的固定阈值宣称稳定。最终音乐码率区间与延迟预算由真机确定。
4. 校验包长、格式代际、序号与解码输出帧数。损坏数据不得直接进入音频设备；晚到的旧流或旧配置数据不得混入新流。丢包掩蔽如采用，须有明确适用条件、时长上限及计数，不冒充原样样本。
5. 保护停止、切换和错误路径的输出连续性。缓冲不足先采取已协商的适应策略；链路无法维持时明确暂停/重缓冲或终止，避免输出未初始化内存、错误格式、重复旧块或无界延迟。
6. 物理断连、关蓝牙、超出覆盖范围不可能保证无限连续播放；UI 必须真实报告连接与恢复状态。恢复产生新的当前 owner，并复核设备身份和音频许可。

验收需要真实播放、接收提交/消耗帧计数与可复现的数字或录音证据；至少覆盖一小时稳定播放、无线干扰、手机锁屏、CPU 压力、文件传输并行、切歌/暂停/恢复、连接替换和断连。分别记录 underrun、解码错误、掩蔽、重缓冲、端点丢失与恢复时间，结合听音检查异常噪声；单元测试和“连接成功”不能替代这项验收。

## 对当前实施的影响

当前 SBAU v1 codec 已包含原文件绑定、PCM、独立 Opus 消息和蓝牙 attachment 路由。消息类型存在并不证明所有平台已完成对应收发、原生输出与真机验收。继续保持一个音频业务会话，把链路作为受认证的 transport adapter 接入；各平台、USB／专属 Wi-Fi／蓝牙链路以及两类音源的实现与验收状态分别记录。

### 2026-10-21：Apple 有限长度 Opus 编码边界

`SkyBridgeOpusStreamEncoder` 复用已有 libopus 1.6.1 和 `SkyBridgeOpusEncoder`，接收已按明确兼容策略转换好的 48 kHz PCM16 单声道／立体声；不承担文件解码、重采样、账户授权获取或传输。固定 20 ms、128/192/256 kbps CBR，与现有解码 profile 对齐。构造时读取原生 lookahead；仅在已提交帧数与声明长度完全一致时补足编码延迟和最后一包。接收端按源帧数和 pre-skip 裁掉编码延迟／尾部填充。依据 [RFC 7845 第 7 节](https://www.rfc-editor.org/rfc/rfc7845.html#section-7) 的有限输入计数规则，采用零填充；这不是保真或无缝切歌保证。

每次最多提交 4096 帧，只保留一个 960 帧缓冲；每包同步交给调用方。错误、取消、输出失败与回调重入都是终态，不能被调用方捕获后继续完成。授权谓词在原生计算及输出回调前后检查，且重入屏障先于授权回调安装。资源释放须等当前调用退出；无隐式任务、重试或整曲缓冲。源 EOF／完整性检查仍属于未来的文件源所有者，编码完成回执不代表源已校验、对端已收到或物理播放完成。

宿主和真实 iPad Pro M4（iPadOS 27.0.1、ARM64）均通过同一组 24 项 XCTest，零失败／跳过；不能相加当作 48 项不同用例。其中新增 11 项包含 54 组声道／码率／短尾长度组合：不同提交分块产生相同编码包，与直接原生连续编码一致；实际解码后首尾计数和 PCM 与连续参考一致。另有两分钟输入的有界分块／最终计数检查，不是两分钟实时无线播放。原有 13 项编码控制和 Android 记录包解码回归继续通过。最终 iPad 构建无编译警告，结果包无运行期警告，原生库摘要与既有 provenance 的 iOS slice 相符。

真机使用隔离、无声的测试宿主。最初 Swift Package 无宿主模式不支持设备测试，随后测试宿主缺少自动生成的 Info.plist；两次失败保留。首次通过后出现 AppIntents 元数据提取警告，给隔离宿主声明相应系统框架后，完整 24 项复验通过且警告消失，没有禁用检查。Xcode 的 `invalidDigitCount(94232)` SDK 记录诊断在前一日测试日志中已存在，保留为外部工具问题。临时测试应用已卸载，既有 SkyBridge 应用未替换。命令、源摘要、失败记录、最终 xcresult 和清理回执位于 Android 工作区的 `artifacts/apple-opus-file-20261021/`。

这层尚未接入 iOS 播放页或蓝牙发送会话，未宣告新播放能力。iOS 文件解码／兼容转换、受认证蓝牙会话、后台生命周期以及真实接收端输出仍需继续实现和验收；原文件严格路线保持其现有契约。

### 2026-10-21：Apple 共用 FLAC 文件解码与关闭边界

`SkyBridgeAudioFile` 现在由 Mac 和 iOS 共用同一份 `AudioFlacPCMDecoder`、完整验证 witness 和有界 PCM 读取实现。Mac 原有名称仅为共享类型别名，现有严格输出泵仍使用原始整数 PCM；共享模块不依赖 HAL、账户服务或网络。验证后逐块读取，最多返回 65,536 字节，并保留源文件所有者负责句柄与安全作用域清理的边界。此模块可用于后续 iOS 蓝牙兼容转换，但当前尚未接入该发送会话。

这一提取前先复现了缓存生命周期缺陷：关闭已提交文件后，原生缓存仍能返回下一帧；上层 PCM 缓存也会在关闭或文件大小变化后继续返回样本。原生步进现在在同一源 reader 执行器内检查存活和身份，上层读取在前后再次检查源及自身关闭状态，失败保持终态。另一个确定性反例在授权回调里调用 decoder.close，触发 `os_unfair_lock` 递归加锁并崩溃；现在该同步回调只标记关闭，当前步进停止交付并在退出时释放原生状态，外部关闭仍等待占用结束。保留原始断言失败和系统崩溃记录。

libFLAC 仍锁定 1.5.0 同一 commit、源码树、官方归档摘要和许可证。配方新增独立的 iOS ARM64、模拟器 ARM64/x86_64 配置，与 Mac ARM64 一起形成三种平台 slice；只合并同一模拟器平台的架构。每种配置均检查实际 hardening 编译参数、Mach-O 平台和最低系统版本，iOS 两种 SDK 版本进入锁文件；上游单元测试在 Mac 执行。依据 [CMake Apple 交叉编译规则](https://cmake.org/cmake/help/v4.3/manual/cmake-toolchains.7.html#cross-compiling-for-ios-tvos-visionos-or-watchos) 和 [Apple XCFramework 组合规则](https://help.apple.com/xcode/mac/current/en.lproj/dev544efab96.html)，设备与模拟器分别配置。`--stage-only` 可先验证候选而不覆盖现存产物，替换前保留了旧产物与证明；未修改编解码生产源码或放宽严格模式。

共享源码在 Mac 和真实 iPad Pro M4（iPadOS 27.0.1、ARM64）各通过同一组 31 项 XCTest，零失败／跳过。包含 4/8/12/16/20/24/32-bit、1/2/6/8 声道固定样本的逐字节 PCM 对照、CRC／MD5／丢帧拒绝、计数、截止时间、取消、关闭以及实际文件句柄回归。编译启用 warnings-as-errors，设备结果无运行期警告；Xcode 仍输出前一日已出现的 `invalidDigitCount(94232)` SDK 记录诊断，不能因此宣称工具日志完全无诊断。早期隔离测试包遗漏一项常量声明的构建失败也保留，不能算作产品反例；最终共享测试直接消费产品模块，无该声明替身。临时无声测试宿主已卸载，既有 iPad 产品版本与安装地址未变化。

随后根工程的完整 `SkyBridgeCore` 构建和 49 项文件播放相关回归通过，覆盖现有播放泵与共享模块的调用关系。该回归包含上面的 31 项，不能累加为互不重叠的用例。根测试链接仍有一条重复 rpath 警告；同一警告在前一日 `ios-membership-persistence-20261020/mac-green-01.log:16` 已存在，相关 linker 设置未变，未通过禁用警告处理它。上述工具诊断保留为既有问题。

证据位于 Android 工作区 `artifacts/apple-file-pcm-20261021/`，包含旧实现反例、完整源摘要、原生配方与 provenance、Mac 日志、真实设备 xcresult 和清理回执。此结果证明文件解码与生命周期组件，不证明完整 iOS 应用接入、网络／蓝牙连续播放、模拟器运行或兼容 DAC 的原格式物理输出。

### 2026-10-21：Apple 蓝牙兼容模式的 PCM 转换边界

`AudioCompatiblePCMConverter` 是显式有损路线的串行转换组件，不改变严格原文件路线。接收 8–384 kHz、明确单声道／立体声布局的整数或浮点 PCM，拒绝未知位置、多声道隐式混音、非有限值及非零的声明外填充位。每次输入／输出最多 4096 帧；48 kHz 且有效精度不超过 16-bit 的整数输入不加抖动，PCM16 对照保持逐样本一致。需要重采样或降低有效精度时，最终仅进行一次带 TPDF 的 PCM16 量化，饱和次数单独计数。随机种子只控制音频噪声，不参与任何身份或授权。

组件复用系统 `AVAudioConverter`，请求 Mastering、最高质量与 normal priming；遵循 [Apple TN3136](https://developer.apple.com/documentation/technotes/tn3136-avaudioconverter-performing-sample-rate-conversions) 的带输入回调转换接口。真实 iPad 的算法名称读回为 nil；独立 AudioToolbox 探针确认算法属性写入成功，读取返回 `kAudioConverterErr_PropertyNotSupported`，质量 127 和 priming 则可读。完成记录将其明确记为 `unavailable`，不能宣称算法名称已经确认；若读回了不符的算法、质量或 priming，仍拒绝运行。此处没有按失败重建或切换算法。

有限输入须另行处理尾部。Mac 原生探针的 216 个组合中，有 78 个输出比既定向上取整计数少一帧。iPad 更明显：441 帧、8 kHz 音源应输出 2646 帧，旧结束路径仅取得 1032 帧。独立原生探针使用连续或暂停输入、三种分块均复现同一不足，且 primeInfo 没有提供可用尾长，不能把 native EOF 当作输出完整证明。现在源所有者先验证真实 EOF；转换器再提供有界静音延伸，取足 `ceil(sourceFrames × 48000 / sourceRate)` 后立即停止。静音只作为滤波输入，超出音源时长的样本不量化、不发送；最多接受一秒源时间的额外输入，耗尽预算仍不足则失败，不把缺失帧补成成功。

源过长／不足、输出异常、取消、授权撤销、回调重入及下游错误都是终态。授权在原生操作与交付前后检查，回调触发的取消须等当前原生调用退出再释放对象。组件不持有文件、获取账户权限或建立蓝牙连接；完成记录不是源完整性、对端接收或物理播放回执。

最终 Mac 根工程新增 15 项回归通过；真实 iPad Pro M4（iPadOS 27.0.1）通过包含这 15 项及原有文件／FLAC 检查在内的 46 项测试，零失败／跳过、无运行期警告。检查包含 60 组采样率／短尾长度／声道组合的不同分块对照、独立连续原生参考、首尾脉冲时间位置、96→48 kHz 的通带／混叠与声道隔离、TPDF 统计和错误生命周期。抗混叠检查的 -60 dB 门槛仅是该固定合成样本的回归下限，不是通用音质或听音结论。原始六项、随后两项真机失败和诊断探针均保留；没有把诊断宿主的完成状态计入产品测试。根工程既有重复 rpath 警告和 Xcode SDK 记录诊断仍保留。

源摘要、命令、原始失败、独立探针、最终 xcresult 及清理回执位于 Android 工作区 `artifacts/apple-compatible-pcm-20261021/`。临时宿主已卸载，既有 SkyBridge 应用的版本与安装地址相同；期间出现的另一个测试应用未操作。该阶段尚未接入 iOS 文件发送任务或受认证蓝牙会话，真实连续／后台播放仍待实现与验收。

### 2026-10-21：iOS 文件到 Opus 的所有权与会话绑定

`IOSOpusFileSource` 将已持有、摘要固定的 WAVE／FLAC 文件、兼容 PCM 转换和有限长度 Opus 编码组合为同一个文件源。它只用于显式有损路线：原文件严格模式保持原来的发送与输出路径。当前接收已知且非零、最多四小时的单声道／立体声文件；传统 WAVE 没有位置掩码时记录所作的布局解释，显式不支持的布局仍拒绝。FLAC 在准备阶段先完成完整解码校验。发送器须等认证接受及输出就绪后调用 `start`，之后按请求逐包推进；没有不受发送背压约束的后台生产者。包队列有硬上限，源文件关闭、实际转换／编码计数一致且缓冲排空后才返回 EOF；该完成值不代表对端接收或播放。

停止和授权撤销会使源失效，已编码的缓冲包也须重新检查。关闭超时保留同一清理任务及文件所有者，后续调用只能等待其真实结束，不能将任务取消当作句柄已释放。回归覆盖真实文件和原生编解码、短尾计数、输出声道与合成音频相关性、背压、变更的源、坏 FLAC、撤销及关闭超时；没有向声卡输出测试音频。

iOS 主音频会话新增与 Mac 相同的蓝牙绑定取得入口，绑定仍由已完成 Finished／配对提交的原会话密钥和本次 offer／route 派生。真实 iPad 反例表明：缺少实际写出完成后的 `commitSent` 会让已收到路由的协商一直返回 `notReady`；修复后才能一次性取得绑定。共享协商同时增加已签发绑定的存活检查，Mac 和 iOS 的子通道均调用它；MAIN 的 Stop 在同一协商锁内使后续检查失败，原生传输清理另行确认。Mac 原回调在发送／接收两种角色及两个 Stop 方向上均未拒绝旧绑定，四个断言失败已保留，修复后通过。

文件源的隔离 Mac 与 iPad 检查各通过 23 项；完整 iOS 工程随后在真实 iPad Pro M4（27.0.1、ARM64）通过 53 项定向测试，其中包含前述 23 项，不能累加；Mac 根工程的绑定、收发会话与通道回归通过 73 项。设备结果零失败／跳过、无运行期警告。完整工程编译与测试启用 warnings-as-errors；缺失旧依赖缓存的失败和已有 SDK 记录诊断另行保留，替代缓存的八个依赖版本与源码内容已对照锁文件核验。隔离宿主的测试 target 曾缺少 AppIntents 系统框架声明，产生元数据提取警告；补齐该 target 的依赖后重新构建通过，未关闭提取或警告检查。Mac 根测试仍保留前一日已出现的重复 rpath 警告。证据在 Android 工作区 `artifacts/ios-opus-file-source-20261021/`。这些是文件源和会话绑定的接入证据；该轮尚未实现的蓝牙拨号与发送调度进度见下，真实跨设备连续播放及 Windows 实体输出仍未完成。

### 2026-10-21：Apple 蓝牙主动连接及握手授权

`BluetoothAudioConnector` 只使用已认证 MAIN 交换签发的一次性 source binding，按其中服务 UUID 扫描、连接一个候选并打开给定动态 PSM；发现结果和系统配对都不发放音频权限。四步子通道认证全部完成后才可取得媒体通道，握手本身的每次原生部分写出也必须检查有效账户授权。连接有有限期限，不启用系统自动重连；停止、撤销、父连接丢失和迟到的连接回调不能复活原操作。

[Apple 的取消接口](https://developer.apple.com/documentation/corebluetooth/cbcentralmanager/cancelperipheralconnection(_:)) 是异步操作。实现保留 central、peripheral 和已交接的流，等待该本地连接的终止回调及原生流工作线程退出；观察超时保留同一所有者供显式清理重试，不宣称其他应用共享的物理链路已断开。关闭不能等待自己所在的连接任务，重复关闭调用共享一次清理。

Mac 根工程与真实 iPad 上的隔离宿主各通过同一组 58 项连接、握手、双向加密流与清理检查；iPad 没有跳过或运行期警告。第一轮 iPad 的一项弱引用即时释放断言失败，但同一测试随后观察到两条原生流已关闭；改为在有界关闭确认之后检查释放，保留关闭状态及对象释放断言。另一个测试的信号量优先级等待触发诊断，改成有起始屏障的受控主线程忙碌；没有压低生产优先级或关闭诊断。原失败与成功结果均保留于 Android 工作区 `artifacts/apple-bluetooth-dial-20261021/`。这些测试注入蓝牙驱动回调，真实 Foundation 流及密码学仍运行；尚未验证真实无线扫描、CoC 打开、持续吞吐、后台或扬声器播放。

### 2026-10-21：iOS 蓝牙文件发送调度与页面接入

`IOSOpusFileSendSession` 将文件源、连接绑定、主动 CoC 连接、账户租约及续期接到已有产品会话。已持有文件先验证身份／元数据，MAIN 仅发送一次 Opus offer 并接受 route／Stop；媒体在独立认证子通道传输。子通道须按序给出与 offer 匹配的固定窗口 Accept 和 OpusOutputReady，之后才创建转换器／编码器；原 opcode 11 仍为 16 包，新文件缓冲模式见下节。包序号、固定码率长度、源 EOF、转换后 48 kHz 帧数、原生 pre-skip／尾部填充、压缩字节摘要和两种完成回执分别检查。信用允许覆盖一个真实在途写出，但成功计数只在该写出完成后推进；提前到达的内容或播放回执不能掩盖发送失败。

同一流的源文件、连接器及账户租约都有明确所有者。授权撤销和停止同步退休效果检查，取消不伪装成正常文件 EOF；真实关闭失败保留所有者并阻止新播放，显式重试只重新确认原操作清理。续期在输出就绪后启动并延续同一租约；关闭媒体与文件先于等待未完成的账户 I/O。MAIN 的即时拒绝曾抢在本地 offer 写出恢复之前到达，使提交协商只返回 closed，UI 误报连接变化。现由共享邮箱保留已认证 Stop 原因，提交仍失败且不签发子绑定；发送器保留拒绝原因并避免回送无意义 Stop。

入口仍在设备的“在电脑上播放音频”页。只有已认证接收端同时声明 Opus 接收与蓝牙附着能力，才显示“通过蓝牙播放文件”；按钮使用现有文件选择器、持久服务和账户提供器。该接入阶段的蓝牙文件默认值为 Opus 48 kHz／192 kbps；当前 iOS 候选已调整到 128 kbps，持续播放仍未通过，见下节。页面分别显示原文件格式和传送格式，明确说明压缩与转换；原文件严格模式的入口和实现保留。包内增加蓝牙用途说明和中／英／日文界面文本。当前文件路线仍为前台使用，进入后台明确停止；[Core Bluetooth 后台模式文档](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html)只支持相应事件处理，不能据此宣称持续编码或无线播放已受系统保障，后台稳定性仍需原生验证。

### 2026-10-21：iPad 到 Mac 的原生蓝牙试验及持续播放缺口

真实 iPad 与 Mac 已通过产品主会话的身份、账户与播放准入，再经加密 GATT 读取和核对本次 PSM，建立独立认证的蓝牙 CoC。主会话在这些试验中使用 USB，因此不能将它们记为不依赖其他链路的纯蓝牙首次连接。1 秒极低音量文件通过了本地验收入口及普通文件选择器；发送端取得匹配的内容校验和播放完成回执，Mac 报告资源已释放。这些结果只覆盖已记录的短样本，不证明听音质量或严格原格式输出。

### 2026-10-26：iOS 蓝牙文件后台任务候选

iOS 蓝牙文件服务已接入现有的有限后台任务所有权。系统实际启动与提交均完成后才运行发送器；拒绝、过期和取消会停止并等待原发送器清理，不延长账户租约，也不创建替代连接。`bluetooth-central` 只声明中心端后台事件能力，不能替代系统执行期限或真实无线验收。此实现依据 Apple 的[有限任务接口](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados)与[蓝牙后台行为](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html)；在当前设备上的持续可用性仍是假设，需实际切换应用和播放验证。

进度来自已完成的文件准备、实际写出的 Opus 包和接收端退还的包额度。总包数绑定实际编码器的预跳过量及源帧数，不用时间推算播放进度；最后的播放回执和清理仍单独占有完成条件。原文件模式继续使用原有哈希字节、文件字节和原生源帧计数，两种任务不能混用进度。界面保留有损转换说明，并显示当前系统后台状态；未取得系统任务的旧系统路径仍要求前台。

旧实现已复现切后台立即停止的反例；修复后完整 iOS 工程的 232 项相关回归通过，iPhoneOS 构建及原签名身份核验通过。系统任务回调、无线连接及声卡进度在这些检查中是受控边界；原生文件、编解码和加密流实际执行。这一包尚未安装到 iPad，不能把上述结果当作真实后台蓝牙播放通过。保留此前前台十分钟的成功及更早断流反例，蓝牙默认接收能力的产品验收开关没有因此放开。证据位于 Apple 工作区 `artifacts/ios-bluetooth-background-20261026/`。

### 2026-10-29：iOS 握手发布期间的首帧丢失
